Held Timers Architecture

On-demand timer triggering for Test Studio — hold every timer at instance creation, fire it by BPMN element on request.
Branch feat/exclusive-job-dispatch-lease, 2026-09-23. Alpha, REST v2 only, x-added-in-version: 8.10, x-scope: physical-tenant. Not merged.

TL;DR

  • Problem: a BPMN timer fires on its own due date, so a recorder replaying against a real cluster can neither pause at a timer nor advance it on command.
  • Fix: holdTimers: true at instance creation keeps every timer out of the due-date index, so the scheduler never sees it. POST /v2/process-instances/{key}/timers/trigger with { "elementId": … } fires one on demand.
  • Addressed by (instance, element), not by timer key — no API exposes one. Exactly one match required.

Why not just shorten the timer? Editing the model to fire "soon" changes the artifact under test and still cannot pause the process for inspection. Holding leaves the model untouched and puts the firing moment under the recorder's control.
What "held" means, field by field Engine
Concern Behavior
Scope holdTimers is set once on the root process instance at creation. Every timer in that instance tree — including called children — inherits it, because children read the root's flag.
The flag held is a boolean on TimerRecord (default false), persisted on the stored TimerInstance by TimerCreatedV2Applier alongside processInstanceKey and handlerNodeId (the BPMN element id).
Timers covered Anything created while the instance is active that goes through subscribeToTimerEvent: intermediate catch events, boundary timers, event sub-process start timers. Process-level start timers are not owned by an instance — out of scope.
Revoking a hold Not possible. No engine command hands a held timer back to the scheduler; the instance must be cancelled instead.
Firing one: the trigger contract new endpoint
POST /v2/process-instances/{processInstanceKey}/timers/trigger 
{
  "elementId": "Event_159hbtn"
}
elementId is the BPMN element id on the canvas. Exactly one held timer must match: 1 → 204, 0 → 404, >1 → 409 INVALID_STATE.
✓ Addressable from the model. Test Studio has the instance key and the element id; it never has the engine's internal timer key. The endpoint speaks the recorder's vocabulary and the engine translates.
Why exactly one? A multi-instance body or a loop can produce several live timers for the same element id. Firing an arbitrary one would be non-deterministic, so the contract makes the caller's ambiguity explicit rather than silently picking.
Tenant, not just permission. The check is cslCheck.checkAuthorizationAndTenant(...) — PROCESS_DEFINITION / UPDATE_PROCESS_INSTANCE plus the resolved timer's tenantId. A caller outside the owning tenant gets NOT_FOUND, not FORBIDDEN, so the rejection cannot be used to probe for timers in another tenant.
The held-timer index RocksDB column family 
// ZbColumnFamilies ordinal 166, PARTITION_LOCAL
// (renamed in place from the retired TIMER_KEY_TO_ELEMENT_INSTANCE_KEY)

key   = DbCompositeKey<
          processInstanceKey: DbLong,  // scan prefix
          DbCompositeKey<elementInstanceKey: DbLong, timerKey: DbLong>

Every part of the key is immutable for the life of a timer. The element id is deliberately not in it — it is mutable, and baking it in desyncs the index on migration (see Bug 6 →). The resolver reads the element id back off each stored timer instead, where it is always current.

Hydrate before authorize. The resolved timer writes bpmnProcessId, tenantId, processDefinitionKey and elementInstanceKey onto the command value first, so the authorization check reads the command's own fields and the rest of processing is identical to a scheduler-issued fire.
Every external command is authorized. The command API always stamps request metadata, so a client-issued TIMER TRIGGER can never take Path A. Timer intents other than TRIGGER have no processor and are rejected.

Seven bugs: three between "unit-green" and "works on a live cluster", four from review. The engine logic was correct throughout — the breaks were at the boundaries, and each surfaced as an error pointing away from its cause.
Bug 1 · Strict exporter template rejection Storage
Symptom: the exporter's bulk request fails with strict_dynamic_mapping_exception on held / holdTimers. Records stop flowing to the secondary store — rejected, not silently dropped.
Fix: add each field to both the ES and OS templates and recreate pre-existing indices (Implementation →).
Bug 2 · Command routed to the wrong partition Gateway / broker-client
Symptom: intermittent 404 NOT_FOUND on a timer that is genuinely held — it "worked" whenever the request happened to land on the right partition.
Root cause: BrokerTriggerTimerRequest never called setKey(...), which is what decodes the target partition from a key. Without it addressesSpecificPartition() is false and BrokerRequestManager round-robins the command; on a partition that does not own the instance the held index is empty, so the engine correctly says NOT_FOUND.
Fix: request.setKey(processInstanceKey), the same pattern BrokerCancelProcessInstanceRequest uses. Routing only — Path B ignores record.getKey().
Bug 3 · Command API refused the value type Broker command API 
// UNSUPPORTED_MESSAGE from the broker
Expected to handle only messages of type
[JOB, DEPLOYMENT, PROCESS_INSTANCE, …],
but received one of type 'TIMER'
Root cause: CommandApiRequestReader only decodes a value when ValueTypes.isUserCommand(valueType) is true. Timers were only ever triggered internally, so TIMER was never in USER_COMMANDS.
Fix: add ValueType.TIMER to USER_COMMANDS; UnifiedRecordValue.fromValueType(TIMER) already maps to TimerRecord. Safe, because every external command carries request metadata and is forced through resolve-and-authorize.
Bug 4 · The trigger command skipped the tenant check Security
Symptom: a principal holding UPDATE_PROCESS_INSTANCE on a definition with the same bpmnProcessId in tenant A could fire a held timer in tenant B — a cross-tenant write on a brand-new public endpoint.
Root cause: the processor called the permission-only cslCheck.check(...). Every other process-instance command calls checkAuthorizationAndTenant(...); this endpoint had no tenant dimension at all.
Fix: switch to checkAuthorizationAndTenant(...) with the resolved timer's tenantId and a NOT_FOUND rejection (trigger contract →).
Bug 5 · Resuming a suspended instance re-armed its held timers Engine state
Symptom: suspend a holdTimers instance, resume it, and every held timer gets a due-date entry and fires on its own. The feature silently stops working.
Root cause: store() branched on held, but resume() did not — it upserted into TIMER_DUE_DATES guarded only by get(...) != null, writing the entry a held timer never had.
Fix: resume() skips held timers. Covered by shouldNotScheduleHeldTimerOnResume and shouldKeepTimerHeldAcrossSuspendAndResume.
Bug 6 · Migration desynced the held index Engine state
Symptom: after a migration moved a held timer to a new element id, the trigger could not find it. The old entry leaked permanently, and a later held timer on the old element id would read as AMBIGUOUS forever.
Root cause: the index key contained elementId, a mutable field. TimerInstanceMigratedApplier rewrites handlerNodeId via update(), which only touches TIMERS, so remove() later wrapped the new element id and the old row was never deleted.
Fix (structural, not another maintenance site): take the element id out of the key — (processInstanceKey, elementInstanceKey, timerKey) are all immutable — and match the element id against each stored timer instead. Nothing is left to desync.
Bug 7 · A client trigger hung while the instance was suspended Engine
Symptom: a trigger sent during suspension got no response at all — the caller waited for a resume that might never come.
Root cause: onSuspended returned BUFFER for every command. That is right for the scheduler's internal trigger, which carries a timer key and a due-date entry to suspend; a client command carries neither, and no response writer runs on a buffered command.
Fix: onSuspended and onResuming return REJECT for a non-internal command, keeping the existing behavior for the scheduler's. The caller gets INVALID_STATE immediately.

Why CPT needs the switch Motivation
In MANAGED and SHARED mode CPT owns the clock (increaseTime / setTime), so nothing fires until the test says so and there is nothing to hold. In REMOTE mode the cluster clock runs: a PT5S timer fires before the replayed step reaches it, and pinning the shared cluster's clock would stall every other instance on it.
And there was no fallback. INCREASE_TIME does not fire a held timer, so until this work a recording that used the switch had no replayable form in any mode.
What shipped Java client · format · runtime
1 · open the instance with held timers
client.newCreateInstanceCommand()
  .bpmnProcessId("order-fulfillment")
  .latestVersion()
  .holdTimers(true)
  .send().join();
2 · fire one held timer
client.newTriggerTimerCommand(processInstanceKey)
  .elementId("escalation")
  .send().join();
Modelled on newReleaseJobCommand: no gRPC stub, send() goes straight to the HTTP client. The element id is the whole body, so elementId() returns the final step — a trigger without one is never valid.
REST-only, by design. gateway.proto has no counterpart for either. newTriggerTimerCommand has no gRPC form at all, and holdTimers throws UnsupportedOperationException over gRPC rather than dropping the switch — a silent drop would let the cluster clock fire the timer the recording meant to drive. Leaving gRPC out is acceptable because REST is the client default and the switch only matters in REMOTE mode.

Three decisions worth the ink Design
Decision Why
TRIGGER_TIMER carries a process instance selector as well as an element selector The call-activity instructions take an element selector alone because they resolve to a job, and JobSelector already carries a process definition id. A timer is addressed by an instance key, which only a process instance selector can produce. UPDATE_VARIABLES pairs the two for the same reason and is the precedent followed here.
Select the element by elementId, never elementName For a boundary timer the id belongs to the boundary event while the element instance belongs to the activity it is attached to — so resolving a name through the element-instance API would find nothing for the commonest held-timer shape. buildTimerElementId throws otherwise, mirroring buildCallActivityStubJobSelector.
The trigger runs inside the await block A held timer may not exist yet when the step is reached, and the engine answers 404 until it does. triggerTimer issues the command inside awaitProcessInstance, as completeJob does: AwaitilityBehavior.untilAsserted is configured with ignoreExceptionsInstanceOf(ClientException.class) and the rejection arrives as ProblemException → ClientHttpException → ClientException, so it retries instead of failing.
Teardown Leak prevention
A held-timer instance parks like a reserved one: its timer never fires on its own and the hold cannot be revoked, so a test that fails before triggering leaves the instance on a shared or remote cluster forever. 
// CreateProcessInstanceInstructionHandler
final boolean isolated =
    reserveJobs
    || stubCallActivities
    || holdTimers;
The runner cancels every isolated instance in a finally, so the failure path is covered too.
Conflict detection Warn, never reject
holdTimers plus INCREASE_TIME or SET_TIME fails mildly: nothing starves, the held timer simply does not fire and the next assertion times out with nothing pointing at the cause.
holdsTimersAndMovesTheClock logs before the first instruction runs and points at TRIGGER_TIMER. It does not fail the run: holdTimers is per create instruction, so a test case may legitimately hold one instance's timers while advancing the clock for another.
Still open Out of scope
Gap Status
Revoking a hold No engine command exists, so there is nothing for the client or the format to expose. This is where the timer story is genuinely narrower than reserved jobs, which have RELEASE_JOB.
Multi-instance and parallel branches Two live held timers on one element id reject with 409 at the engine and the instruction replays as a failure. The CPT-level shadow of the missing occurrence index JobSelector also lacks, deferred the same way.
End-to-end coverage on a running engine Coverage is unit-level.
