⏺ The analysis confirms your suspicion — there are no ordering guarantees.
  Here's the breakdown:

  No Liveness Gate Exists

  The StreamProcessor lifecycle in StreamProcessor.java does this in sequence:

  1. Completes replay (snapshot + log)
  2. Calls onRecovered() on all lifecycle listeners — this is where
  IdentitySetupInitializer schedules the setup command at 0L
  3. Immediately calls processingStateMachine.startProcessing() — begins
  consuming new commands from the log

  There's no wait between steps 2 and 3. The scheduled task from step 2 competes
   with incoming commands for execution.

  Why runAtAsync(0L, ...) Doesn't Help

  - It runs in a separate async actor pool, so the scheduling request itself is
  queued asynchronously
  - The actual task execution depends on processScheduledTasks() being called,
  which runs on a periodic interval (~100ms tick), not on-demand
  - Meanwhile, ProcessingStateMachine.tryToReadNextRecord() is already pulling
  commands off the log stream

  So yes — a CreateProcessInstance command that arrives on the log could
  absolutely be processed before the identity setup command.

  Why It Works Anyway (for Identity)

  The identity setup is idempotent and additive — it creates default
  roles/tenants/users. If a command arrives before identity setup, it still
  works because:
  - The engine doesn't reject commands for missing identity state
  - The setup just ensures defaults exist; it doesn't gate functionality

  Implications for Ordinal Initialization

  This is a different situation. If ordinals aren't initialized yet and a
  CreateProcessInstance arrives, you'd assign ordinal 0 (or no ordinal), which
  breaks the routing design. You have a few options:

  1. Use replay state, not scheduled commands — Initialize the ordinal counter
  from ProcessingState during replay. By the time startProcessing() is called,
  the counter is already in memory. No race.
  2. Make ordinal assignment lazy — On first ProcessInstanceCreation, if no
  active ordinal exists, create one inline (synchronous in the processing
  pipeline, not scheduled). This sidesteps the scheduling race entirely.
  3. Gate at the processor level — The ProcessInstanceCreationCreateProcessor
  could check if ordinals are initialized and reject/retry if not. Ugly but
  deterministic.

  Option 1 is cleanest — the ordinal counter state should come from the
  ProcessingState (column family in RocksDB), restored during replay, so it's
  always available before any new commands are processed. The scheduled command
  pattern is the wrong fit here because ordinal state is a prerequisite, not a
  background setup task.

  Want me to dig into how ProcessingState is restored during replay to confirm
  option 1 is viable?

  - This stores: current active ordinal number, lifecycle per ordinal

  2a. Interfaces

  getLifecycle(int ordinal)
  - MutableOrdinalState extends it: void create(int ordinal), void activate(int

  2b. DB Implementation
  - DbOrdinalState — follows the DbClockState singleton pattern
  - Column family key: DbInt (ordinal number)
  - Column family value: DbOrdinalValue (lifecycle enum, created timestamp)
  - Also store a singleton "current active ordinal" entry (key = special

  2c. Wire into ProcessingDbState
  - Add MutableOrdinalState ordinalState field
  - Initialize in constructor: ordinalState = new DbOrdinalState(zeebeDb, 
  transactionContext)
  - Add getter to both ProcessingState and MutableProcessingState interfaces

  Phase 3: Event Appliers

  - OrdinalCreatedApplier — sets ordinal lifecycle to PENDING in state
  - OrdinalActivatedApplier — sets lifecycle to ACTIVE, updates "current active
  ordinal"
  - OrdinalClosedApplier — sets lifecycle to CLOSED
  - Register all in EventAppliers.registerOrdinalAppliers()

  This is what makes replay work. During replay, these appliers reconstruct the
  ordinal state from the log on top of the RocksDB snapshot. By the time
  startProcessing() is called, getActiveOrdinal() returns the correct value.

  Phase 4: Processor

  OrdinalProcessor implements DistributedTypedRecordProcessor<OrdinalRecord>

  processNewCommand(CREATE):
    - Only executes on partition 1
    - nextOrdinal = state.getActiveOrdinal() + 1
    - stateWriter.appendFollowUpEvent(CREATED)
    - stateWriter.appendFollowUpEvent(ACTIVATED)  // or separate command
    - commandDistributionBehavior.distribute(command)  // send to all partitions

  processDistributedCommand(CREATE):
    - On receiving partition: apply the ordinal locally
    - stateWriter.appendFollowUpEvent(CREATED + ACTIVATED)
    - commandDistributionBehavior.acknowledgeCommand(command)

  Phase 5: Wire Processor into EngineProcessors

  In EngineProcessors.java, register the processor similarly to how
  ClockProcessors or IdentitySetupProcessors are registered:

  OrdinalProcessors.addOrdinalProcessors(typedRecordProcessors, state, writers,
  ...);

  Phase 6: Ordinal Assignment in ProcessInstanceCreation

  This is where it all connects. In ProcessInstanceCreationCreateProcessor:

  // Already available from state — no race, no scheduling
  int activeOrdinal = processingState.getOrdinalState().getActiveOrdinal();
  processInstanceRecord.setOrdinalKey(activeOrdinal);

  The ordinal is set synchronously during command processing, not via a
  scheduled task. Since state is restored before processing begins,
  getActiveOrdinal() always returns the right value.

  Phase 7: Bootstrap (First-Ever Startup)

  On a brand-new cluster, no ordinal exists yet. Two options:

  Option A — Default ordinal 0 means "no ordinal" (already your convention)
  - getActiveOrdinal() returns 0 from empty state
  - Process instances get ordinal 0 → routed to the main index (legacy behavior)
  - Partition 1 issues ORDINAL.CREATE(1) via the scheduled initializer pattern
  (like identity setup)
  - Even if a few PIs get ordinal 0 before this, that's fine — they go to the
  main index

  Option B — Block-free lazy init
  - First CreateProcessInstance on p1 checks getActiveOrdinal() == 0, issues
  ordinal 1 inline
  - Slightly more complex but avoids even a single PI with ordinal 0

  I'd recommend Option A — it's simpler, consistent with your existing 0 = 
  legacy/no ordinal convention, and the identity setup pattern already proves
  this works well enough in practice.

  Phases 1-3 can be built and tested in isolation. Phase 4-5 need the protocol +

⏺ The distinction is straightforward:

  TypedRecordProcessor<T>

  The base interface. Has one method that matters:
  processRecord(TypedRecord<T>). Used for commands that are partition-local —
  they execute on one partition and that's it.

  Examples: ProcessInstanceCreationCreateProcessor,
  ProcessInstanceCancelProcessor, ResourceDeletionDeleteProcessor

  DistributedTypedRecordProcessor<T>

  Extends TypedRecordProcessor and overrides processRecord() with a router that
  splits into two methods:

  - processNewCommand(command) — called when the command originates on this
  partition (first time). Typically: validate, apply state, send client
  response, then call commandDistributionBehavior.distribute(command) to
  replicate to other partitions.
  - processDistributedCommand(command) — called when the command arrives from
  another partition. Typically: apply state locally (no re-validation, no client
   response, no re-distribution), then call
  commandDistributionBehavior.acknowledgeCommand(command).

  The routing logic checks command.isCommandDistributed(), which works by
  comparing the partition ID embedded in the command's key against the current
  partition ID. If they differ, it's a distributed command.

  Examples: TenantCreateProcessor, RoleCreateProcessor, SignalBroadcastProcessor
   — anything that needs cluster-wide state consistency.

  For Ordinals

  DistributedTypedRecordProcessor is the right fit. Partition 1
  creates/activates ordinals (processNewCommand → distribute), other partitions
  receive and apply them locally (processDistributedCommand → acknowledge). This
   matches the identity/authorization pattern exactly.

⏺ inQueue() is the right choice for ordinals. Here's the difference:

  unordered()

  - Sends to all partitions in parallel, no ordering
  - Used for: clock pin/reset, signal broadcasts — operations where order
  doesn't matter

  inQueue(queueId)

  - Commands are enqueued per partition and distributed one at a time, in order
  - Next command only distributes after the previous one is acknowledged
  - Used for: identity changes (IDENTITY queue), deployments (DEPLOYMENT queue),
   global listeners

  Why ordinals need inQueue()

  Ordinal activations are a causal sequence — ordinal 2 must never be applied
  before ordinal 1 on any partition. With unordered(), if two ordinals are
  activated in quick succession, partition X could receive and apply ordinal 2
  before ordinal 1, corrupting the active ordinal state.

  DistributionQueue entry or a string. Let me check what exists.
