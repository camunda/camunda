## Open question for DS-team review

**Sign-off on the `PartiallyExpandableDataTable` → DS `DataTable` rewrite.**

`carbon-compat`'s `DataTable` adapter explicitly refuses the render-prop pattern this component is built on (`children?: unknown`, `@deprecated`, dev-mode warning). [#59208](https://github.com/camunda/camunda/issues/59208) listed the render-prop `DataTable` as an open question pending DS-team sign-off; the Dashboard hits that exact gap in both `InstancesByProcess` and `IncidentsByError`. PR 5 needs confirmation that composing native DS `DataTable` with `columns`/`data`/`expansion` is the right target before that rewrite starts.

The Dashboard currently paginates by scroll, not by a pager — `useDashboardScrollPagination` drives `onScroll` on a wrapping container. That approach is dropped, not attempted-and-fallback: the DS docs list container-wrapping as an explicit anti-pattern for `DataTable` — its own `Table` wrapper already owns the scroll region, so nesting another scrollable ancestor around it produces double scrollbars. The open question is which of two replacements fits: (1) manual pagination with `pageCount: -1` (TanStack "infinite" mode) driven by a Load-more/Next button, or (2) if scroll-triggered loading is required, an `IntersectionObserver` on a sentinel below the table, triggered by the page's own natural scroll rather than a wrapper around the table. PR 5 should record which one is confirmed and why.

**Sanctioning `carbon-compat` for `Tooltip`.**

`InstancesBar`'s `Tooltip` is the first call site in this repo that would import from `carbon-compat` rather than the native DS component — every other row above either drops the symbol or migrates to a native DS API directly. The adapter (`carbon-compat/tooltip.js`) is a real wrapper over DS's own Radix tooltip primitives and is API-compatible with the existing call site, so it's a mechanically safe SWAP; what's open is whether `carbon-compat` imports are sanctioned for use in this codebase at all, since adopting one here sets precedent for later PRs. Not gating this issue (`carbon-compat/MAPPING.md` describes it as a like-for-like shim), but PR 4 needs a DS-team or tech-lead decision on this before it lands.
