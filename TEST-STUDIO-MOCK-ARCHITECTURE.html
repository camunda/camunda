Test Studio Mock Architecture

Current state vs. engine-level isolation — Job Workers, Connectors & Call Activities

Reconciled with the spike on feat/exclusive-job-dispatch-lease (RESERVED-JOBS-PLAN.md, STUBBED-CALL-ACTIVITIES-PLAN.md), 2026-09-21. Both switches are alpha, REST v2 only, x-added-in-version: 8.11.

TL;DR

  • Problem: Recording a test against a real cluster loses the steps the test is about: a job worker takes every job within milliseconds, and a call activity starts the real child process. Today the only isolation is switching the cluster's workers off, or deploying a stub process definition — both cluster-wide, so two people cannot record at the same time.
  • Fix: two independent switches, both set when the instance is created: RESERVE_JOBS stamps the caller's token on every job the instance creates, so they are served to no worker (Job Workers & Connectors →). stubCallActivities activates each call activity with no child, waiting instead on a job that stands in for the called process (Call Activities →).
  • What Test Studio gets: Both produce ordinary jobs visible in /v2/jobs/search, so a recording session has one inbox of pending decisions. Per item: complete it with variables (mock), or hand it to the real thing — release for a reserved job, runCalledProcess for a stubbed call activity.
  • Status: Implemented and tested on feat/exclusive-job-dispatch-lease, not merged. Alpha, REST v2 only, x-added-in-version: 8.11. Needs an ADR — the call-activity switch changes BPMN execution semantics (Limitations & Verdict →). The Java client and CPT now carry both switches — fluent setters, the reservation token on the job commands, a release command, and JSON test-case instructions that replay in every runtime mode. What is still open in CPT is the cluster purge and the round-trip breaks, not the switches (CPT →).
  • Rejected alternative: A static child process result declared at instance creation is easier to integrate, but it removes the wait state: nobody is there to ask “mock this child, or run the real one?” (card at the bottom of Call Activities →).
  • Where the rest is: Request and response shapes in Orchestration Cluster API changes →; the two switches contrasted in Side-by-Side Comparison →; what the recorder itself still needs — and why the existing CPT mocks are warned about rather than replaced — in Test Studio →.

Alternative considered: static child process result Rejected — review feedback, 2026-09-21

Raised in review of the stub-job design. The concern was that the stub job sits outside how the engine works today: it needs extra logic in both the call activity and the job processors to handle a job that no worker ever runs. This alternative trades some flexibility for a fit that is easier to integrate into the engine.

What it would buy: nothing in the job subsystem is touched — no job type, no worker hiding, no release rejection, no JobResultType.CALL_ACTIVITY, no START_CALLED_PROCESS intent and no incident retry for it, and no job-record protocol churn. A process id absent from the map runs the real child, so recording through a called process still works — per definition rather than per instance.
Why we did not go with it
⚠ It removes the wait state, which is the feature. Test Studio is meant to stop at each call activity and ask the user: mock this child, or run the real child process? A result declared before the instance starts has nobody to ask. Static result cannot host that prompt — it can only replay a decision made before the run began, which is not recording.
⚠ One inbox becomes two. Reserved jobs are meant to give Test Studio a single list of “things waiting for your decision”, polled with /v2/jobs/search and answered with one completion call. A stubbed call activity would appear in that same list. A static result — or any element-level wait that is not a job — would mean a second mechanism and a second list.
⚠ Less expressive where it matters. No per-call-activity-instance mock (a loop, or two call activities calling the same child), no value chosen from what the run has produced so far, no per-instance runCalledProcess, and no way to make the called process fail so the recorded test covers the error boundary event.

Session cleanupUI-owned

What happens — if the user closes the tab or the browser crashes mid-recording:

  • Reserved jobs stay ACTIVATABLE forever (no TTL)
  • Stubbed call activities stay ELEMENT_ACTIVATED forever
  • The instance is parked, but recoverable: cancelling it terminates the element and cancels the stub job unconditionally
  • A reserved job can also be handed back with POST /v2/jobs/{jobKey}/release — but only by whoever still holds the token
✓ Resolution — token recovery is a Test Studio responsibility. Because jobReservationToken is client-chosen and lives for the instance, Test Studio persists it server-side (keyed by the recording session) rather than only in tab memory. On the next session it reloads the token and reattaches to the parked instance by key — no token is ever lost to a closed tab or a browser crash.
Remaining edge — the abandoned recording. The real gap is not a lost token but a user who never finishes the recording and never comes back: the instance then stays parked forever. Mitigate with a soft TTL sweeper (e.g. 24h) and/or a user-facing "abandon test" action that cancels the instance — terminating the element and cancelling the stub job unconditionally.

The gap: instances the recorder does not create Accepted limitation

Both switches are carried on the create command and stored on the root instance record. Anything that makes an instance without that command gets neither — the instance runs with its jobs exposed to every worker and its call activities starting real children. This is one gap with three faces:

Trigger What creates the instance Consequence for recording
Inbound connector (webhook, polling subscription, intermediate inbound) The connector runtime, from outside the engine — it publishes a message or creates the instance itself No job is ever activated for the inbound half, and for an inbound start connector there is no instance to scope anything to
Message start event The engine, on message correlation — POST /v2/messages/publication or a correlating client The instance is born unreserved and unstubbed; the recorder can find its jobs but a real worker will have taken them first
Signal start event The engine, on signal broadcast — and one broadcast may start several instances across definitions Same, plus there is no single instance the caller could even claim: a per-instance token has nothing to attach to
What works today

Start past the trigger. startInstructions already lets the recorder create the instance itself and begin at an element after the start event, so the rest of the process records normally with both switches on. Test Studio already sends this field.

What that costs:

  • The trigger itself is never exercised — no correlation key evaluation, no subscription, no inbound payload mapping
  • The variables the message or webhook would have supplied must be authored by hand, and a wrong guess there is invisible in the recording
  • The recorded test starts where the real process does not, so the CPT test covers a shorter path than the model
Why the engine cannot close it per instance

Any fix has to attach the switch to something that exists before the instance does. Every candidate is a scope wider than one instance — which is the cluster-pollution objection that motivated this design in the first place:

  • Per message subscription — the publisher would carry the token, so the recorder must own the message publication. That covers a message start event but not a webhook, whose payload the connector runtime publishes
  • Per process definition — "reserve every instance of this definition" hits every caller of it, exactly like today's globally deployed stub
  • Per tenant — a dedicated recording tenant that no worker or connector runtime subscribes to. This is the only clean isolation for the start-event path, and it needs no engine change — but it also means the inbound connector never fires, so the trigger still is not recorded

Decision: Test Studio accepts this for now — do not widen the switch. Mocking job workers, connectors and call activities is still a big improvement, and Test Studio's segment testing can exclude these start events by beginning the test past the real trigger via startInstructions. This limits end-to-end process tests for the start-event path, but that is treated as a separate problem needing tenant-level or runtime-level isolation.

Why CPT needs these switches Motivation & problems

A recorded test replays against whatever cluster CPT points at. In MANAGED and SHARED modes CPT spins up its own throwaway cluster, so a cluster-wide mock harms no one. In REMOTE mode — the mode Test Studio runs recorded tests through — CPT replays against a live, shared cluster, where a cluster-wide mock hijacks everyone else's instances. stubCallActivities and reserveJobs keep the stand-in inside your own instance, and CPT must be able to set them.

What breaks in REMOTE mode today — four independent problems. This proposal addresses the first three; the cluster purge is a separate, larger question, called out below.
1 · mockChildProcess deploys a cluster-wide stub
It replaces the called process for the whole cluster, breaking every other instance that calls it — the problem stubCallActivities removes. Proposal: leave mockChildProcess as it is (re-pointing published API would be a breaking change) and add the isolated stub-job instruction alongside it, so isolation becomes a property of which instruction the author chose.
2 · Completing a reserved job sends no token
CPT finds a job and completes it by key — the right shape — but sends no jobReservationToken, so every call on a reserved job is rejected. Proposal: the context mints one token per test run and attaches it to every job command; an unreserved test sets none and is unaffected.
3 · A half-finished isolated instance is never cleaned up
A reserved job or stubbed call activity stays parked until its instance is cancelled, so a test that fails midway leaks it onto the cluster. Proposal: the runner records every instance it creates with either switch and cancels them when the case ends.
4 · CPT purges the whole cluster after every test — out of scope, should be tracked separately
CPT calls POST /actuator/cluster/purge by default and does not check for MANAGED mode, so pointing it at a live cluster wipes it. Tests are kept apart only by timing. This predates the switches and is not part of this proposal.
Two ways to mock in CPT — one isolates, one does not Solution proposal

This proposal gives CPT a second toolkit for standing in for a job, a called process or a worker, alongside the existing mocks. They look similar, but differ in the one thing that decides which to use: do they touch only your instance, or the whole cluster?

Isolated switches new Existing mocks
Isolates your run? ✓ Yes — only your instance ✗ No — affects the whole cluster
How stubCallActivities / reserveJobs hold the job or child inside your instance mockChildProcess deploys a cluster-wide stub; mockJobWorker opens a real worker by job type

Fires Once, on the job you name (per occurrence) A standing rule — every matching job, unbounded

⚠ Don't point both at the same job. An isolated switch hides the job from CPT's own mock worker. So if one test both reserves/stubs a job and registers mockJobWorker / mockChildProcess for it, the mock never sees it and the run hangs until the await timeout. The runner warns you before the first step and names it in the failure — it does not reject the case, because reserving one instance while a mock serves another is legitimate. Pick one mechanism per job.
Both stay supported. The existing mocks are unchanged and are the simplest choice on a disposable MANAGED cluster. Reach for the isolated switches the moment a real, shared cluster is involved — that is the exact hijack they were built to remove.
Proposed API surface Java client · REST v2 · schema
Client API. CPT drives everything through CamundaClient, so the fluent client gains reserveJobs(token) and stubCallActivities(flag) on the create command, withJobReservationToken on complete, fail, throw-error and PATCH, forCallActivity().runCalledProcess() as a third job result, and newReleaseJobCommand(jobKey).
REST-only, by design. gateway.proto has no counterpart for these fields. The new setters write the REST request only, and send() throws UnsupportedOperationException naming the field if the command is sent over gRPC — silently dropping the switch would hand the job to a real worker. newReleaseJobCommand has no gRPC form at all, and there is deliberately no newReleaseJobCommand(ActivatedJob) overload, since a reserved job is never activated.
new fluent method / endpoint / schema variant CPT would need
Read this as two things. Snippets 1–5 are the replay-time CamundaClient calls CPT would make against a live cluster — they carry the token. Snippet 6 is the stored recording that drives them — it captures the user's intent by elementId and holds no token. // hand control to the actual called process
client.newCompleteCommand(jobKey)
  .forCallActivity().runCalledProcess()
  .withJobReservationToken(token)
  .send().join();

  .retries(0).errorMessage("declined")

  .send().join();

  .errorCode("PAYMENT_DECLINED")
  .withJobReservationToken(token)
  .send().join();

Four types. RELEASE_JOB is the only new endpoint; the three call-activity actions — STUB_CALL_ACTIVITY_COMPLETE, STUB_CALL_ACTIVITY_THROW_ERROR and RUN_CALLED_PROCESS — each take an elementSelector and read as what they do to the call activity. They resolve the element to the stub job internally, so no callActivityStub selector flag is needed and COMPLETE_JOB / THROW_BPMN_ERROR_FROM_JOB stay job-only. The format still has no fail instruction; that is a separate gap, not this one.
How one recording is stored — two layers
layer 1 · the create block — decided once, up front 
// the user's session choices live here, not per step
{
  "create": {
    "processDefinitionId": "order-fulfillment",
    "variables": { "orderId": "A-1001" },
    "stubCallActivities": true,   // don't start real children
    "reserveJobs": true          // hold jobs from real workers / connectors

  ...

Both are session-wide switches, so they sit on the instance, not on a step — as two booleans on the CREATE_PROCESS_INSTANCE instruction. No token here: it is a runtime value, minted at replay.

// mock vs real is never a flag — it's a different type

Every step is keyed by elementId — no jobKey, no token. Both are runtime values only known at replay.
Recording → replay. The recording captures intent; the token is runtime. At replay CPT reads the create block, mints one fresh token for the run (only if reserveJobs was true) and reuses it for every instance that run reserves — two runs on one cluster still never collide, and CPT finds jobs by selector rather than by instance. It calls newCreateInstanceCommand with the switches + token, then for each step finds the job by elementId and turns it into the matching client command (snippets 1–5) — attaching the token only when that instance was reserved. That is why the Java snippets show the token everywhere (they depict the reserved recording flow) but the stored JSON shows none.
The three call-activity steps select the element, not the job. Element ids are unique per definition, but a call activity can carry execution listeners, whose jobs share that element id and are hidden by reservation too — so naming the job would be ambiguous. Instead the step names the call activity and CPT resolves it to the job the stub waits on, keeping the engine's internal job type (io.camunda.zeebe:callActivityStub) out of the stored recording. A reserved service-task job is still driven by jobSelector.
Where this leaves non-remote CPT MANAGED / SHARED

These modes start their own throwaway containers — no foreign worker, no other instance to hijack. All four problems above are moot, so the switches are never needed here.

But the recorded instructions still run
  • A recording that uses the switches replays here too — RUN_CALLED_PROCESS, RELEASE_JOB, a stub throw and the create-block switches are parsed and executed the same way in every mode.
  • Run-real-child and release have no mockChildProcess / mockJobWorker fallback, so the client and schema support they need ships for every mode, not just remote.
The other direction — a CPT test opened in Test Studio Lossy round-trip

The goal is two-way: a hand-written CPT test should also open in Test Studio. Both sides share one format, but CPT's always-on mocks (a standing rule that fires N times) and a recording (one action on one job) are different shapes, so the conversion loses information.

Studio → CPT works

COMPLETE_JOB and THROW_BPMN_ERROR_FROM_JOB already match how CPT runs. The format just needs four additions — RELEASE_JOB, a fail-job instruction, runCalledProcess, and the two switches on the create instruction — plus the token fix (problem 2 above).

Connectors round-trip cleanly. A connector is stubbed as a plain job, so nothing is lost across the trip.
CPT → Studio is lossy
  • An always-on mockJobWorker fires an unbounded number of times, so it can't be flattened into a fixed step list — every CPT test runs, but not every one can be recorded.
  • JobSelector has no occurrence index, so when two jobs share an element id (multi-instance, parallel branch, retry) replay is non-deterministic — a break that hurts both directions.
⚠ Three things neither switch reaches. DMN and script tasks are evaluated in-engine, so mocking them still means a cluster-wide stub — the hijack stubCallActivities removes, with no counterpart here. And reservation hides listener jobs, so a test that sets reserveJobs then calls COMPLETE_USER_TASK parks on listener jobs nobody authored.
Verdict. Clean for the common case — linear tests, one occurrence per element, jobs and call activities — but lossy for always-on rules, DMN/script tasks and listener jobs. None of this needs the existing mocks changed; it needs the new instructions, conflict detection, and a UI that is honest about what each instruction isolates.
The two switches, in plain termsTest Studio

Test Studio lets you record a test of a process and replay it later. Two new switches let you fake parts of the process, so you can test it on its own without the real things it depends on:

“Stub call activities” — pretend a sub-process ran, instead of actually running it.
“Mock connectors and job workers” — pretend an outside system replied, instead of really calling it.

On screen this is a handful of pieces: the two checkboxes shown before a run; the switch settings remembered for that run and passed to the engine when it starts; the “fake this step” buttons on the diagram; and buttons to run the real sub-process or hand a step back to the real system.

A saved test is just a list of instructions. The create step stores the two switches (stubCallActivities, reserveJobs), and each faking button — Mock child process, Run real child, Mock connector, Release job — stores its own step. Replay reproduces the same faking; nothing has to be remembered beyond the instructions themselves.

What changes is who executes those instructions. Today Test Studio replays them itself, calling the orchestration cluster API with the switch parameters. The target is to replay recorded tests through CPT instead — which this proposal teaches to drive both switches (CPT →). Either way the saved test is unchanged; only the executor differs.

What a recorded test can contain today

Starting an instance, sending messages and signals, completing jobs and user tasks, throwing errors, resolving incidents, updating variables and assertions — plus the new faking steps: stub a call activity, mock a job or connector, run the real sub-process, and release a step back to the real system.

These faking steps are isolated. They only touch your own test run, so replaying a saved test does not affect anyone else. (The one exception — hand-written mocks that are not isolated — is covered in the last card.)
Remaining UI work Two items

With the switches and faking steps recorded (left), what remains is small:

1 · Let people enter example data

Today the faking buttons send empty data and show no form. They should open a small form to type in example data — the same pattern the normal “Complete job” button already uses. For a connector, the form should ask for the reply the process expects, not a raw technical response (Job Workers & Connectors →).

2 · Remove the outdated warning

A message still says “Call activities are not supported in saved test cases and will fail on replay.” Once stubbing and recording are in place this is no longer true, so it should be removed. This is the one clearly user-visible win.

The “this can affect others” warning Warning UX

There is a second, older kind of mock you can write by hand. Unlike the buttons above, these set up a fake across the whole cluster — for example by deploying a stand-in or opening a real worker — so they can affect other people’s runs. Rather than change how they behave, Test Studio keeps them but warns you that they are not isolated.

The mechanism already exists

Test Studio already recognises these hand-written mock steps. It keeps them in the saved test but does not run them, and it already shows a small warning popover: “This test case contains instructions that aren’t supported in Test mode and will be skipped during execution.”

Only the wording is missing. Distinguish “not supported in Test mode” from “not isolated — sets up a fake for the whole cluster and can affect other runs.”
Where the warning fits

Three existing patterns to reuse rather than invent:

  • The existing warning-message path — a badge on the element plus a problems-table row, whose “actionable solution” slot is the natural home for “use the isolated instruction instead.”
  • The stronger form that replaces the action button with a popover and a docs link — the template if we ever block rather than warn.
  • The disabled-with-a-reason pattern — where to reject the RESERVE_JOBS + MOCK_JOB_WORKER_* combination that starves and hangs rather than failing.
⚠ The limitation this accepts. Test Studio does not really know whether a cluster is production. The only hint is the colour of the cluster’s tag (dev is green, test blue, stage purple, prod red). So “this step is not isolated” is only a warning the user is trusted to act on — nothing blocks it. That is the price of not breaking the older hand-written mocks, and it is listed under Limitations & Verdict →: warn now, decide before general release.

Rule Why
Keep the token for the life of the instance No API returns it; losing it leaves cancellation as the only way out
One fresh, unguessable token per instance Two recorders on one cluster must not collide; it is an isolation label, not a secret
