Probes – specification

Specification for Connector Validation Phase 2, Option E, validated on 2026-11-10. This file is the source of truth for probes: a change found during implementation updates this file first, with a decision number. The Probe specification tab of the Phase 2 doc is its shared summary. The decision record is ADR 001.

Status markers:

  • AGREED – we decided it in discussion.
  • PROPOSED – a proposal by the DRI, not discussed yet.
  • SUPERSEDED – replaced by a later decision; kept struck through so the history stays readable.

Revised on 2026-11-03 after the Define kickoff (2 Nov 2026). The kickoff moved probes from a push stream to long polling, the same model as job activation (D38 to D45). On the same day, the routing key became one opaque probeId (D46), as the Zeebe team proposed, instead of the job type (D36). The POC then fixed the deadline (D49) and the poll shape (D50). Revised again on 2026-11-03 after an audit for implementation (D51 to D66). Revised on 2026-11-04 after a review of the authorization with Security (D67 to D69). Detailed on 2026-11-10 for implementation without context: audit log (D70), activation response, physical-tenant paths, known POC divergences. Revised on 2026-11-12 after the review of the ADR (camunda/camunda#68884): rolling-update risk (D71), secrets in answers (D72), injected-value pointers for the SDK (D73), connector runtime (section 5.2) agreed with Connectors, acceptance tests published in section 13. Open question left: OQ30, the default role for PROBE:CREATE. The questions we discussed, with the reasoning behind each decision, are in Questions discussed.

This spec is the source of truth for the implementation. The POC (draft PR #68078) is a reference, not a base: where they differ, the spec wins, and a change found during implementation updates the spec first, with a decision number.

Known POC divergences, so that code copied from the POC is fixed:

  • The NO_WORKER detail names only "no worker polls this probe ID"; it must also name a missing PROBE:ANSWER (D52).
  • The audit log gives TIMED_OUT and CANCELED the default result SUCCESS; it must be FAIL (D70).

1. Purpose​

A probe is a short request from a client to a worker. The client waits for the answer in the same HTTP request. A probe has no process instance and is not a job.

The client sends the probe to a probeId, an opaque string that a worker registers, as a job worker registers a job type. By convention it is <operation>/<template>, for example validate-configuration/io.camunda:aws-credential:1. The worker fetches probes the way it fetches jobs: by long polling. The engine does not interpret the probeId or the input.

The first use is configuration validation ("Is this AWS credential valid?"). Metadata retrieval (dropdown values, schemas) and task testing are later epics (section 11). The mechanism must support them without engine changes.

Workers keep their security design: they connect out to the cluster. The cluster never connects to a worker.

2. Terms​

TermMeaning
ProbeOne request from a client to a worker, and its answer.
Probe ID (probeId)The routing key of a probe: an opaque string that a worker polls for, as a job worker polls a job type. Convention: <operation>/<template>, for example validate-configuration/io.camunda:aws-credential:1 (D46).
InputOne FEEL expression that evaluates to a context. It carries what the worker needs (D11).
Probe workerA worker that polls for probes of one or more probeIds, in one request (D50). A connector runtime opens one probe worker for all the probeIds it answers.

D36A probe is routed on a job type, field jobType: the type of the worker. For credential validation, the input carries the credential type. Credentials are used by many connectors, each with its own job type, so a client validating a credential on its own has no job type to send.SUPERSEDED by D46
D37No operation field. What the worker should do is part of the input, whose shape the worker of the probeId defines. The engine does not know about operations: there is no closed enum, no permission per operation, and no check of the shape of data. Kickoff. Supersedes D15.AGREED
D38REST only, with long polling: workers fetch probes with POST /v2/probes/activation, which mirrors POST /v2/jobs/activation (same long polling in the gateway, same notification when work is available). No gRPC, no SSE, no stream. Kickoff Q9. Supersedes D10, D34, D35.AGREED
D39The lifecycle mirrors jobs: CREATED, then ACTIVATABLE in engine state until a poll collects it, then ACTIVATED until the answer. At collection the engine checks the secrets, as JobBatchCollector does: all cached, the values go into the activation response only; one missing, the probe is parked and its resolution requested, and it becomes ACTIVATABLE again when the resolution completes.AGREED
D40NO_WORKER is decided at the deadline. A probe that no poll collected before its deadline ends with 404 NO_WORKER. A probe that was collected but not answered ends with 504 WORKER_DID_NOT_ANSWER. One timer, no pickup timeout: when no worker exists, the client waits for its whole requestTimeout. Supersedes D4.AGREED
D41If the gateway cannot hand an activated probe to the worker (the poll's connection broke), it sends YIELD, and the probe becomes ACTIVATABLE again for the next poll, as the gateway reactivates jobs it could not deliver. No limit on the number of yields: the deadline bounds the probe. Supersedes D17.AGREED
D42ANSWERED never carries data: only outcome, worker, and message for ERROR. The response to the client is written from the ANSWER command, which the exporters skip. Metadata answers (business names, possibly large) stay off the exported records. The audit entry for a validation loses the validation code. Supersedes the data part of D16.AGREED
D43A probe worker that gets an error on its poll, including a 404 from a cluster without probes, retries with exponential backoff (backoffSupplier), as the job worker does. It does not stop. Kickoff Q5.AGREED
D44The Java worker API mirrors the job worker: newProbeWorker().probeId(probeId, handler), repeated for each probeId the worker answers, then options, then open(). One probe worker polls all its probeIds in one request (D50). See section 5.1. Supersedes D3, D33.AGREED, refined by D46, D50
D45Names kept by the kickoff: the resource is probes, the worker action is answer (POST /v2/probes/{probeKey}/answer). Kickoff Q3 and Q8.AGREED
D46A probe is routed on probeId, one opaque string. The client sends it in the request; a worker polls for it, as for a job type; the engine matches it by exact string equality and never interprets it. It is a free string: any worker may register any probeId, so probes are a general synchronous channel to workers. Convention for Camunda workers, documented but not enforced: <operation>/<template>, for example validate-configuration/io.camunda:aws-credential:1 or fetch-field-options/io.camunda.connectors.Slack.v1. The PROBE resource ID and the audit description are the probeId. Proposed by the Zeebe team on 2026-11-03. Supersedes D36.AGREED
D47When a SaaS and a hybrid runtime register the same probeId, the first poll that reaches the partition collects the probe, as for jobs with the same type. Documented limitation. A hybrid runtime that must answer alone registers its own probeId. A worker selector comes later.AGREED
D48The engine checks only the envelope of an answer: outcome and the length of message. data is opaque, because the engine does not know what a probeId means. D42 stays: ANSWERED never carries data.AGREED
D49The gateway computes the probe's deadline when it receives the request (now + requestTimeout) and sends it to the engine as an absolute time. The engine never recomputes it from its own processing time; a CREATE processed after its deadline ends at once with TIMED_OUT (reason NO_WORKER). The gateway keeps waiting T + 500 ms and the Java client T + 1 s. With long polling, every probe without a worker ends exactly at its deadline, so a relative deadline let the gateway answer 504 DEADLINE_EXCEEDED before the engine's 404 NO_WORKER under load (seen on the POC). The engine schedules its time-out check at most 400 ms ahead while a probe is pending (below half of scheduledTaskCheckInterval), because the platform runs tasks due later on a 1 s tick, up to 1 s after their time. Known limits: clock skew between gateway and broker above about 400 ms brings back the 504; the hop depends on the platform interval and is derived from it; under heavy backpressure the engine can still miss the 500 ms margin, as for any command. Closes OQ16.AGREED
D50One activation request carries a list of probeIds, and one probe worker polls all of them. This diverges from jobs, where a poll names one type. Probes are rare, so almost every poll returns empty: with one poll per probeId, that empty traffic grows with the number of IDs (for example, 100 IDs, 3 partitions and a 10 s poll timeout give about 30 empty activation commands per second per runtime). With a list, it is one poll per runtime. The engine checks PROBE:ANSWER per ID and collects only probes of the IDs the poller may answer (D14). A held poll wakes on a notification for any of its IDs. maxProbesToActivate and maxProbesActive count across all IDs. Closes OQ34.AGREED
D51No feature flag: probes are available as soon as the release ships them; the endpoints are alpha (section 4.3). Known limit during a rolling update: until every broker runs the new version, a CREATE or a poll that reaches an old broker is rejected, and the client gets an error instead of an answer. Workers back off (D43).AGREED, refined by D71
D52A poll silently skips the probeIds the poller has no PROBE:ANSWER on, as job activation skips what the worker may not activate. Clients then get 404 NO_WORKER at the deadline, so the NO_WORKER detail names both causes: no worker polls the probeId, or the worker lacks PROBE:ANSWER on it.AGREED
D53A request too large for one log batch (EXCEEDED_BATCH_RECORD_SIZE) gets 413 PAYLOAD_TOO_LARGE: on CREATE, the client gets it at once; on ANSWER, the worker gets it, and the Java client then sends ProbeAnswer.error("The answer is too large."), so the client gets 200 with outcome: ERROR instead of waiting for the deadline. Closes OQ14.AGREED
D54A probeId is 1 to 256 characters, without whitespace, and not * (the authorization wildcard, section 8). A poll lists 1 to 100 distinct probeIds. Anything else gets 400 INVALID_ARGUMENT, on CREATE and on activation. The Java builder rejects a duplicate probeId with IllegalArgumentException.AGREED
D55When sending an answer fails with 503 or a network error, the Java worker retries with its backoffSupplier until the probe's deadline, then logs and gives up. 400, 403, 404 and 409 are never retried; 413 follows D53.AGREED
D56The Elasticsearch and OpenSearch exporters ship a PROBE and a PROBE_BATCH template, both off by default (index.probe, index.probeBatch = false). The audit log does not depend on them (section 7).AGREED
D57A probe may run more than once: a CREATE retried on another partition after a lost response (D22) or a yield (D41) can hand the same request to two workers. No idempotency key. So probes are read-only in phase 2; task testing must revisit this (OQ33).AGREED
D58Phase 2 delivers the core in camunda/camunda first: records, engine, gateway and REST, OpenAPI, Java client, exporters, audit log, and the PROBE resource in the Identity UI. The connector runtime (section 5.2) follows in camunda/connectors; its design was agreed with Connectors on 2026-11-12.AGREED
D59The answer is a union of three shapes, with a discriminator on outcome (OpenAPI oneOf). Worker request: OK → {outcome, data}, data required; UNSUPPORTED → {outcome}; ERROR → {outcome, message}, message required. Any other combination gets 400 INVALID_ARGUMENT. The client's 200 response has the same three shapes, plus worker. Closes OQ23.AGREED
D60The engine finds references by FEEL detection, as for input mappings (D28). The request has no explicit secretRefs or clusterVars lists; they come back only if parsing a large input proves too slow. Closes OQ32.AGREED
D61A hybrid runtime's probe handler replaces the legacy {{secrets.X}} syntax from the runtime's own configuration, as it does for its jobs. The engine passes this syntax through as text. Connector runtime work (D58). Closes OQ35.AGREED
D62Probes use 504 (WORKER_DID_NOT_ANSWER, SECRET_RESOLUTION_TIMEOUT, DEADLINE_EXCEEDED), documented in the OpenAPI, although the guidelines' response-code table has no 504. Closes OQ24.AGREED
D63Metadata epic: the connector runtime caps a metadata answer (for example 1,000 items and 256 KB) and pages longer lists with a page token. Not phase 2. Closes OQ13.AGREED
D64Metadata epic: read permission on a SECRET_REFERENCE cluster variable covers its secrets, so a Modeler user who may use a saved connection can fill a dropdown without SECRET:READ on each secret. Validation keeps SECRET:READ (D14). Not phase 2. Closes OQ17.AGREED
D65Clients build the input in one place, with a helper that writes user-entered values as FEEL string literals, so a value never becomes an expression. Hub work. Closes OQ20.AGREED
D66CREATE checks permissions before it evaluates: (1) PROBE:CREATE on the probeId and the tenant, else 403; (2) the input parses as FEEL with no imprecise reference, else 400; (3) SECRET:READ on each secret found, else 403; (4) the input evaluates to a context, else 400. A caller without PROBE:CREATE never makes the engine parse or evaluate.AGREED
D67The client needs SECRET:READ on each referenced secret, not a reveal permission. Confirmed with Security on 2026-11-04. Closes OQ29.AGREED
D68CREATE does not check CLUSTER_VARIABLE:READ on referenced cluster variables: PROBE:CREATE covers them, as EXPRESSION:EVALUATE does for the expression endpoint. Secrets reached through a cluster variable still need SECRET:READ (D67). Confirmed with Security on 2026-11-04. Closes OQ31.AGREED
D69The Connectors role gets PROBE:ANSWER on * by default. Confirmed with Security on 2026-11-04. The default role for PROBE:CREATE stays open (OQ30).AGREED
D70Audit log mapping: CREATED → CREATE, ANSWERED → COMPLETE, TIMED_OUT and CANCELED → CANCEL with result FAIL; category ADMIN; entity type PROBE; entityKey = the probe key; entityDescription = the probeId. The existing actor configuration applies unchanged, as for jobs: by default only user actors are logged (camunda.auditLog.user logs every category, client and unknown none). So a probe created with a user's token gets its CREATE entry; a probe created by an M2M client, the ANSWERED entry (the worker is a client) and the TIMED_OUT entry (written by the engine, no actor) are logged only when the operator enables those actors. The Phase 2 metric "every validation has an audit entry" holds for user-created probes with the default configuration.AGREED
D71Rolling update, in addition to D51: the new PROBE and PROBE_BATCH events are unknown to a broker of the previous version. An old follower that must replay one is unhealthy until it runs the new version; Raft replication goes on meanwhile. If leadership moves back to an old broker that must replay a probe event, or process a probe command that is still pending, the partition stalls until that broker is updated. Worker backoff (D43) does not help there. The risk is accepted, as for any new record (docs/zeebe/rolling_updates.md). From the review of camunda/camunda#68884.AGREED
D72The cluster never writes a secret value to a record: the engine keeps placeholders and puts values only into the activation response (D12). What a worker sends in data and message is its own: the PROBE:ANSWER command is written to the log as sent, and skipping it in the exporters (D42) does not keep it off the replicated log. A worker must not put injected values into its answer. The Java client's default ERROR message removes them (D30); data is not checked (D48). From the review of camunda/camunda#68884.AGREED
D73The activation response carries secretPointers: the JSON pointers of the input leaves into which the engine injected a secret value, taken from the references the engine found at CREATE (D28). No secret names and no values. The Java client removes the values of these leaves from ActivatedProbe.toString() and from the default ERROR message (D30). A leaf that mixes a secret with other text is removed whole; a message that holds only part of such a leaf is not caught, so a handler must not build messages from secret values. Divergence from jobs, which have no such field: only the probe SDK promises this removal. From the review of camunda/camunda#68884.AGREED

4. Client API​

POST /v2/probes

Request:

FieldTypeRequiredDescription
probeIdstringYesThe routing key, as the worker registered it, for example validate-configuration/io.camunda:aws-credential:1 (D46). 1 to 256 characters, no whitespace, not * (D54).
inputstringYesA FEEL expression that evaluates to a context. The worker that registered the probeId defines the shape of this context (D11). References to camunda.vars.* and camunda.secrets.* follow the input-mapping rules; an imprecise reference is rejected (D28).
tenantIdstringWith multi-tenancyThe tenant.
requestTimeoutint64 (ms)NoHow long to wait for an answer. 0 or absent: the cluster's request timeout. Maximum 30 s (D18).

Example, credential validation:

{
  "probeId": "validate-configuration/io.camunda:aws-credential:1",
  "input": "={region: \"eu-west-1\", accessKey: camunda.secrets.awsKey, secretKey: camunda.secrets.awsSecret}"
}

With a saved connection, the input is the cluster variable: "input": "=camunda.vars.env.awsProd".

Answer: {"outcome": "OK", "worker": "connectors-saas", "data": {"status": "FAILURE", "code": "UNAUTHORIZED", "message": "AWS rejected the credential."}}.

Examples for later uses are in section 11.

400INVALID_ARGUMENTInvalid input: expression not valid, not a context, imprecise reference (D28), input blank, probeId not valid (D54), requestTimeout negative or above 30 s (D18).

4.1 Answer endpoint (worker)​

AGREED (D31, D45).

POST /v2/probes/{probeKey}/answer

Request:

FieldRequiredDescription
outcomeYesOK, UNSUPPORTED or ERROR (D9).
dataWith OK only, required thereA JSON object: the result, as the worker of the probeId defines it. The engine does not check it (D48).
messageWith ERROR only, required thereAt most 500 characters (D30).

The body is one of three shapes, chosen by outcome (D59): {outcome: OK, data}, {outcome: UNSUPPORTED}, {outcome: ERROR, message}.

There is no worker name in the body: the engine uses the worker of the poll that collected the probe (D24).

Responses, mirroring job completion:

HTTPCaseFor jobs
204Accepted.Job completion answers 204.
400 INVALID_ARGUMENTInvalid body: unknown outcome, a field that does not fit the outcome (D59), message too long (D48).Invalid variables.
401 UNAUTHORIZEDNot authenticated.Same.
403 FORBIDDENNo PROBE:ANSWER on the probeId (D14, D24).UPDATE_PROCESS_INSTANCE missing.

The REST layer first rejects a malformed body with 400. The engine then checks in this order: the probe exists, the permission and the tenant, the envelope, then the state. So a late answer with a well-formed body always gets 404.

AGREED (D38). Long polling, as job activation.

How it works, as job activation:

  1. The gateway sends PROBE_BATCH:ACTIVATE to every partition of the physical tenant, round-robin (RoundRobinActivateJobsHandler).
  2. Each partition collects ACTIVATABLE probes with one of these probeIds that the poller may answer (D14), checks their secrets (D39), writes PROBE_BATCH:ACTIVATED, and responds with the input injected into the response only.
  3. If no partition returned a probe, the gateway holds the request (LongPollingActivateJobsHandler) until a partition announces a probe with one of these probeIds, or until requestTimeout.
  4. A partition announces a probe when it becomes ACTIVATABLE: at CREATED, after YIELDED, and when its secrets are resolved. The notification uses its own topic, <physicalTenant>-probesAvailable, so a probe does not wake job pollers.
  5. If the gateway cannot send the response to the worker, it sends YIELD for each probe in it (D41), as it reactivates jobs it could not deliver.

Errors mirror job activation (400, 401, 403, 500, 503). 403 means only that the worker asked for a tenant it is not assigned to, as for jobs; probeIds it may not answer are skipped (D52). A cluster without probes answers 404; the Java client retries with backoff (D43).

The gateway has its own LongPollingActivateProbesHandler; the job handlers do not change. A held poll is registered under (physical tenant, probeId) for each of its probeIds, wakes on a notification for any of them, and is removed from every key when it is woken, times out or fails (D50).

Errors and answers​

If the handler throws an exception, the SDK answers outcome: ERROR with a message (D30):

  • Default: the exception's message, with the secret values injected into this probe removed (the leaves named by secretPointers, D73), cut to 500 characters, as the connector runtime does for jobs (OutboundConnectorExceptionHandler).
  • Configurable, as errorMessageProvider for a job worker.
  • Not the plain job worker's default (the stack trace): a probe's message goes into a user's dialog, and a probe always carries injected secrets.

The worker:

  1. Polls POST /v2/probes/activation for all its probeIds in one request (D38, D50, section 4.2).
  2. Runs the handler of the probe's probeId for each probe it receives.
  3. Sends each answer with POST /v2/probes/{probeKey}/answer (D31, section 4.1). On 503 or a network error it retries until the deadline (D55); on 413 it sends a short ERROR (D53).

ProbeAnswer.unsupported();     // outcome UNSUPPORTED (D5)
ProbeAnswer.error(message);    // outcome ERROR, at most 500 characters (D30)

6.2 Which worker answers​

AGREED (D20, D47).

The first poll that reaches the probe's partition collects it, as for jobs. Replicas of one runtime poll the same probeId and are equivalent.

A SaaS runtime and a hybrid runtime that register the same probeId compete: the answer can depend on which one polled first. Secrets are the same in both, because the engine injects them (D12); only network reach differs, for example a JDBC credential for an on-premises database. Documented limitation (D47). A hybrid runtime that must answer alone registers its own probeId. A worker selector comes later.

6.3 Ending reasons​

TIMED_OUT: NO_WORKER, SECRET_RESOLUTION_TIMEOUT or WORKER_DID_NOT_ANSWER. CANCELED: SECRET_RESOLUTION_ERROR.

6.4 Partitions​

AGREED (D22).

  1. CREATE has no key, so it goes round-robin to the next partition of the physical tenant, as expression evaluation. If the request is not accepted, the gateway tries another partition.
  2. A poll goes to every partition, as job activation (section 4.2).
  3. ANSWER and YIELD go to the partition that owns the probe, found from the probe key.
  4. TIME_OUT comes from the partition's own scheduler.
  5. No command distribution: a probe lives on one partition.

Side effect: the secret cache is per node (secret ADR D7). Round-robin spreads probes over nodes, so a secret can miss the cache once per node. The cold path is accepted (D12).

6.5 Input evaluation​

AGREED (D28). A job gets its references in two steps; a probe does both at CREATE.

How jobs do it:

  1. At deploy, VariableMappingTransformer finds the references on the parsed FEEL tree, each with the JSON pointer of the leaf it sits in: SecretReference.parse for camunda.secrets.<name>, ClusterVariableReference.parse for camunda.vars.<scope>.<name>. SecretReferenceLeafPrecisionValidator rejects the deployment when SecretReference.hasImpreciseReference is true.
  2. At job creation, BpmnJobBehavior.mergedSecretReferences uses ClusterVariableJobSecretResolver.resolveInto on the current cluster variable state: a SECRET_REFERENCE variable adds its stored references at the right pointer; a JSON variable or a missing one adds nothing.
  3. During evaluation, camunda.secrets.<name> evaluates to its own placeholder text (secret ADR D3).

At CREATE, after PROBE:CREATE and the tenant are checked (403, D66), the engine:

  1. Parses input as a FEEL expression. Otherwise 400.
  2. Rejects imprecise references with 400, with the deploy rule (hasImpreciseReference).
  3. Detects direct secrets with SecretReference.parse. Pointers are relative to the input context.
  4. Detects secrets reached through cluster variables with ClusterVariableReference.parse, then ClusterVariableJobSecretResolver.resolveInto, with the same scope rules.
  5. Checks SECRET:READ on every secret found in steps 3 and 4 (D14). Otherwise 403.
  6. Evaluates the input with the input-mapping evaluation contexts: secrets become placeholders, cluster variables are available, there are no process variables. If the result is not a context, 400.

What "static" means:

CaseResult
camunda.secrets.<name> or camunda.vars.<scope>.<name> written directly, found at its own leafA reference. Through a cluster variable, only a SECRET_REFERENCE variable counts.
A reference inside a list literal or a context produced by a branchImprecise: rejected with 400, as at deploy.
Text in a string literal, a name built at runtime, a JSON cluster variable spelling a referenceNot a reference: plain text, never resolved. Jobs do the same.
A context produced by a function call or a for … returnNot detected, as for jobs. Its references stay placeholders, so nothing leaks.

8. Authorization​

AGREED (D14, D46, D67 to D69). Open point: OQ30.

New resource type PROBE:

PermissionWhoResource ID
CREATEClientprobeId (D46), or *
ANSWERWorkerSame

At CREATE, the engine checks, in the order of D66 (section 6.5):

  1. PROBE:CREATE on the probeId, and the tenant.
  2. SECRET:READ on each referenced secret, direct or reached through a cluster variable. This is the guard for secrets, because the worker gets values without a secret permission (D12). Kept as agreed at the kickoff ("READ will be enough") and confirmed with Security; no reveal permission (D67).
  3. No check per cluster variable, as the expression endpoint (ExpressionEvaluateProcessor checks only EXPRESSION:EVALUATE): PROBE:CREATE covers them (D68).

At poll and at ANSWER, the engine checks with the poller's claims, as for jobs (BpmnJobActivationBehavior.isAuthorized):

  1. PROBE:ANSWER on the probeId, and the tenant. At poll, a probe that the poller may not answer is not collected. At ANSWER, a missing permission gets 403 and another tenant gets 404.
  2. No secret permission (D12).

ANSWER means "receive the secrets used with probes of this probeId". Grant it only to the runtimes that serve that probeId. Because probeId is a free string (D46), any worker with ANSWER on * receives every probe's secrets.

Default roles: Connectors PROBE:ANSWER on * (D69). Which roles get PROBE:CREATE is OQ30; the proposal is users who manage connections PROBE:CREATE on * and SECRET:READ, and Admin all.

No permission per operation: the engine does not interpret the probeId (D46). Wildcards are only *, so there is no grant per operation prefix. A probeId can never be * (D54).

The PROBE resource type comes from camunda-security-library, which must be released first (section 12). The Identity UI lists PROBE with CREATE and ANSWER in its authorization screens (D58).

9. Secrets​

AGREED (D12, D39). The engine follows the central secret resolution ADR (docs/adr/secrets/001-central-secret-resolution-architecture.md), as for jobs:

  1. At CREATE, the engine detects the references and evaluates the input (6.5, D28). The probe record carries the references and their JSON pointers, never a value.
  2. When a poll collects the probe, the engine reads each reference from the store's cache only, as JobBatchCollector does for jobs.
    • All references cached: the engine injects the values into the activation response only. The log and the state keep the placeholders.
    • A reference missing: the poll skips the probe, the engine parks it and requests its resolution (SECRET_REFERENCE:RESOLUTION_REQUESTED). The store answers with the command RESOLUTION_COMPLETE or RESOLUTION_FAIL; when the event RESOLUTION_COMPLETED is processed, the probe becomes ACTIVATABLE again and the engine announces it, as for waiting jobs.
  3. A resolution failure (event RESOLUTION_FAILED) creates no incident, because there is no process. The engine ends the probe and answers 400 SECRET_RESOLUTION_ERROR with the job incident's message without the incident part (D13). It names the placeholder only, never the value.
  4. The deadline covers the time spent parked. A probe still parked at its deadline gets 504 SECRET_RESOLUTION_TIMEOUT.

Consequences:

  • A worker receives the values without any secret permission. The CREATE check on the client is the guard (section 8).
  • A cold cache costs a few hundred milliseconds: the resolution, then a new poll after the notification.
  • Staleness: a secret changed in the store is used with its old value for up to the cache TTL (default 20 minutes). Clients should say so in their error message.

  • Answer size: D7. Too large: 413 (D53). For metadata, see D63.
  • Timeout: AGREED (D18), see 10.1.
  • Backpressure applies to CREATE, activation and ANSWER.
  • Clients cache answers and send probes on a user action, not on each key press.

10.1 Timeout​

AGREED (D18).

requestTimeout, in milliseconds, has the same name and meaning as in create-with-result:

  • 0 or absent: the cluster's request timeout (default 15 s), clamped to the cap.
  • Cap: 30 s. A negative value or a value above the cap gets 400. A probe stays in engine state until its deadline, so without a cap a client could fill the state.
  • The deadline covers everything: waiting for a poll (D40), parked for secrets (D12), yields (D41), and the worker's work.
  • The worker sees the deadline (ActivatedProbe, 5.1), so a handler can bound its own calls.

Each layer waits longer than the layer below, so that the client gets the engine's answer and not DEADLINE_EXCEEDED:

LayerWaits
Engine deadlineT
Gateway, for the broker's responseT + 500 ms
Every client of POST /v2/probes (Java client, Hub, Modelers), its HTTP requestAt least T + 1 s; the API documentation says so

The engine deadline T is absolute: the gateway computes it when it receives the request (D49), so queueing and input evaluation cannot push the engine past the gateway.

AT5The input has a secret reference in a list.HTTP 400 INVALID_ARGUMENT. No probe is created.
AT6The client has no SECRET:READ on a referenced secret.HTTP 403. No probe is created.
AT7A referenced secret does not exist in the store.HTTP 400 SECRET_RESOLUTION_ERROR, with the name of the secret.
AT8The worker collects the probe and never answers.HTTP 504 WORKER_DID_NOT_ANSWER at the deadline. A late answer gets 404.
AT9The only runtime has no PROBE:ANSWER.The runtime collects nothing. HTTP 404 NO_WORKER at the deadline.
AT10The worker closes its connection before the activation response arrives.The gateway yields the probe. The next poll collects it.
AT11A connection with secrets.No secret value in the log, the exported records or the response.
AT12Audit and export.One audit entry at creation and one at the end. PROBE records in every exporter whose probe index is on (Elasticsearch and OpenSearch: off by default). No data in ANSWERED.
AT13Operate, Tasklist and the search API.No validation shows.
AT14Two physical tenants.A probe goes only to the workers of its physical tenant.
AT15A job worker and a probe worker in the same runtime.A job worker never gets a probe. A probe never starts a job handler. A probe does not wake the job pollers.
AT16A hybrid runtime with its own probe ID.A probe with this probe ID goes to the hybrid runtime. A result in less than 2 seconds for 95% of validations.
AT17A worker on a cluster without probes.The worker retries with exponential backoff. It does not stop.
AT18One worker polls two probe IDs in one request.It collects the probes of both. Each probe goes to the handler of its probe ID.
AT19A probe ID that is blank, *, longer than 256 characters or with whitespace. A poll with 0 or 101 probe IDs.HTTP 400 INVALID_ARGUMENT.
AT20The answer does not fit in one log batch.The worker gets 413. The client gets HTTP 200 with outcome ERROR at once.
AT21Sending the answer fails once with 503.The worker retries. The client gets the answer.
AT22The engine processes CREATE after its deadline.CREATED, then TIMED_OUT. HTTP 404 NO_WORKER. Two audit entries.
AT23An answer with outcome ERROR and data, or OK without data.The worker gets 400 INVALID_ARGUMENT.
AT24A CREATE without PROBE:CREATE and with an input that is not valid.HTTP 403. The engine does not evaluate the input.

Success metrics:

  • 95% of validations give a result in less than 2 seconds, on SaaS, Self-Managed and hybrid.
  • The security test finds 0 secret values in the log, the exported records and the client responses.
  • Each accepted validation has an audit entry.
  • We have less connectors in failure due to misconfiguration
