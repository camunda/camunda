Status: Proposal. Every decision below is a current proposal, to be reviewed with the customer before it is accepted. Option A (variable metadata) is the chosen way to declare a variable sensitive. Option B (name pattern) and the combination of both options are fallbacks we offer to the customer (D2).

Deciders

  • Konstantinos Mylosis

Purpose: Record how a process variable is declared sensitive, what the engine persists for it, where and how its value is redacted, which records and fields are covered in which order, and what the feature does and does not guarantee.

Audience: Engineers working on the engine variable and mapping behaviors, the exporter pipeline, the Camunda and RDBMS exporters, the v2 REST API, Operate and Tasklist; authors of custom exporters; AI agents reasoning about why a value is an empty string in secondary storage or still readable somewhere.

Related: product-hub epic #3805 (Redact). Companion artifacts: the Variable Protection Proposal and the Variable Records Matrix. The matrix, the source of truth for which records and fields carry variable data, is part of this ADR (Appendix A, D9).

Context​

Sensitive data ends up in process variables because the process needs it to route, decide and call the next system. Today a variable cannot be declared sensitive, and its value is written in plain text to every downstream store: the secondary storage, the raw record indices, Optimize and any custom exporter.

The standing advice to keep sensitive data out of Camunda is a liability for regulated customers (card numbers, personal data). They need the value inside the engine, but not in Elasticsearch, OpenSearch, RDBMS or the UI.

Constraints​

The following constraints shape the decisions below:

  1. The engine needs the real value. FEEL, conditions, mappings, DMN and job workers all operate on it. Destroying it before the log append would break execution.
  2. A value reaches many places. One variable lands in a named VARIABLE record, in the variables maps of roughly 26 command and event records, in error text that quotes it, and in values derived from it.
  3. Every exporter must be covered, including customer-built ones. The exporter SPI has no "rewrite" hook, only accept or reject.
  4. Protection modes beyond redaction are planned, so the declaration must extend to them without a new mechanism.

D1. Redaction applies on export only; primary storage keeps the plain value​

The engine processes the real value. The exported copy carries no value. The Raft log, RocksDB, snapshots and backups stay plaintext.

Rejected: engine-side destruction before the append. It is the only option that also clears the log and state, but:

  • it destroys the value for execution (FEEL cannot branch on it, workers never receive it), and
  • it makes the declaration replicated engine state, because the transform must be deterministic across replay.

D2. A variable is declared sensitive through variable metadata (variablesMetadata)​

Decision: option A. Sensitive variables are identified by metadata sent with the variables, not by their names. It is the better product: protection is explicit, per variable, extensible to other modes and visible in the API. The remaining decisions (D3 to D8) describe option A.

variablesMetadata is the working name of the property on API requests and on records that carry a variables map. It is keyed by variable name and holds a list of protection modes per variable:

"variablesMetadata": {
  "cardNumber": { "protectionModes": ["REDACT"] }
}

The metadata of a single variable is a metadata property holding the same { "protectionModes": [...] } object. It is used where one variable is described: on VariableRecord (the existing VariableRecordValue#getMetadata()) and on the variable results of the read APIs (D4). The translation is deliberate: a request or document-carrying record has many variables and so a map next to variables, a variable record or result has one and so a single metadata.

  • protectionModes is a list so that modes combine. REDACT is the mode delivered first. MASK and ENCRYPT are planned and are not part of this decision beyond leaving room for them.
  • Other metadata fields (the proposal shows propagationBehavior as an example) may be added later. Their names and semantics are not decided here.
  • Protection is sticky. It is stored with the variable, so a later write that omits the metadata does not remove it (D5).
  • The BPMN model can declare protection on input and output mappings, and the engine applies it to the mapped variable. The Modeler presentation is illustrative and not yet confirmed.

Option B (name pattern) is the lighter alternative: a variable whose name matches a configured pattern is redacted. It is not part of this decision. Appendix B describes it and compares it with option A. If the customer decides to proceed with option B, this ADR is revised.

D3. API: variable metadata on every endpoint that writes variables​

Every v2 REST endpoint that accepts variables also accepts variablesMetadata next to it. Process instance creation is the first one:

POST /process-instances
{
  "processDefinitionId": "order-process",
  "variables": { "cardNumber": "4111111111111111" },
  "variablesMetadata": {
    "cardNumber": { "protectionModes": ["REDACT"] }
  }
}

Each key must be the name of a variable set in the same request. A key without a matching variable, or an entry that is null or has no valid protectionModes, is rejected with a 400. A variable without an entry has no metadata on creation, and keeps the metadata it already has when it is set again.

The same property is added to the other endpoints that carry variables:

  • set variables on an element instance (PUT /element-instances/{elementInstanceKey}/variables)
  • job completion
  • user task completion
  • message publication and correlation
  • signal broadcast
  • conditional evaluation
  • process instance modification
  • ad-hoc sub-process activation

The list is derived from every request schema that carries a variables object, and the Variable Records Matrix (D9) is kept in step with it. The first two endpoints (create instance and set variables) ship in M1, the rest in M2 (D10).

gRPC and the Java client. Variables also enter through the gRPC gateway (CreateProcessInstance, SetVariables, CompleteJob, FailJob, ThrowError, message and signal commands) and the Java client built on it. The same declaration is added there, so a value written through them can be marked and is redacted like one written through REST. Each gRPC request message that carries variables gains the matching variable metadata field, and the Java client exposes it. The exact wire shape is settled in the protocol work. An endpoint that has no metadata field cannot protect its values, so the guarantees below hold only for the endpoints and RPCs delivered by the milestones (D10).

D4. API: variable search introduces a metadata field​

Today the variable search and get results carry only the value. A redacted value is returned as an empty string (D8), so the value alone does not tell a client that the variable is protected. The variable results therefore gain a metadata field that holds the protection modes of the variable:

POST /variables/search
{
  "items": [
    {
      "name": "cardNumber",
      "value": "",
      "metadata": { "protectionModes": ["REDACT"] }
    }
  ]
}
  • The field is added to the results of POST /variables/search, GET /variables/{variableKey}, POST /user-tasks/{userTaskKey}/variables/search and POST /user-tasks/{userTaskKey}/effective-variables/search, and later to the decision-instance and incident searches. metadata is always present, and protectionModes is an empty list for a variable that is not protected.
  • For a redacted variable the value is an empty string and the metadata contains REDACT. Operate and Tasklist read it and show [REDACTED] (D8). Clients must check metadata.protectionModes before they use value.
  • The exporters persist the modes with the redacted value, and the search layer returns them. This is part of M1 for the Camunda and RDBMS exporters (D6).
  • Cluster variables already return a generic metadata bag of string and number values. The name is kept for consistency. The exact shape for process variables, and how it relates to the cluster variable bag, is settled in the protocol work and not here.

D5. Engine: records carry the variable metadata​

The metadata is not an API-only concept. The record properties are enhanced with the same variablesMetadata, so that the declaration travels with the data through the log and reaches the exporter pipeline:

  • VariableRecord carries the protection modes of the variable it describes in its metadata (M1).
  • Records with a variables map (the category B records in D9) carry a variablesMetadata map keyed by variable name next to it. The engine propagates the metadata from the command to the VariableRecord it produces (M2).
  • The engine reads and writes the metadata in its Processors and Behaviors and persists it per variable in primary storage, which makes protection sticky (D2).

D6. Exporter: a sanctioned redaction step in the broker exporter pipeline​

Every exporter must be covered, including customer-built ones, and the exporter SPI has no "rewrite" hook, only accept or reject. The broker exporter pipeline therefore gets a sanctioned transform step that runs before any exporter sees the record.

Mutating the record from inside an exporter works in practice, but it is undeclared and order-dependent, and is not relied on.

The Camunda and RDBMS exporters persist the protection modes together with the redacted value (M1), so that the read APIs can return them (D4).

Rejected: field replacement inside the Camunda exporter handlers, or inside both of our serialization chokepoints. Both miss custom exporters. Replacing in the handlers additionally needs six or more write sites kept in step and misses the raw indices Optimize imports.

D7. Redact once in the RecordExporter, before the export fan-out​

The record is redacted once, after the engine has processed it and before it is handed to any exporter.

Where. The redaction runs in the RecordExporter, which the ExporterDirector calls for every logged event. It is the single point where the event is decoded once and passed to each exporter in turn. It does not run in the per-exporter dispatch in ExporterContainer, which would run the transform once per exporter over a shared mutable record.

How. The RecordExporter replaces the protected values with an empty string (D8), using only the variable metadata the record carries (D5). It does not look up engine state. The protection modes stay on the exported record so that the exporters, the read APIs and the UI can tell a redacted value from an absent one (D8).

Result. Every subscriber receives the redacted record: the Camunda exporter, the RDBMS exporter, the raw ES/OS exporters (and so Optimize), and custom exporters.

Consequence: an operator cannot keep a plaintext copy in one destination and a redacted copy in another. That is intended.

D8. What a redacted value looks like, and where the UI gets its text​

A redacted variable is exported with an empty string "" as its value and its protection metadata. Operate and Tasklist show [REDACTED] when the metadata contains REDACT. The API returns the empty string together with the metadata. value stays required and non-nullable in the REST schema, so the response shape does not change for any client.

Why an empty string. Making value nullable is a breaking change under the REST API guidelines (section 2.7 of docs/rest-api-endpoint-guidelines.md) and changes the generated client types for every consumer, for example string | null in the TypeScript SDK, including consumers that never enable redaction. Redaction is opt-in, so an existing consumer only meets the empty string after it starts redacting variables. The "REDACTED" sentinel was rejected because it can collide with a real value and duplicates the metadata, without being safer for clients that parse value.

What customers need to know. The value of a redacted variable is an empty string, not null and not a marker text. metadata.protectionModes is the source of truth, so a client that processes value must check it first for any variable that can be protected.

The full matrix is Appendix A of this ADR. It lists each record with its category, the scenario and the REST endpoints that write and read it, and the variable-carrying field. It lives in the ADR so that it is reviewed and versioned with the code. The Variable Records Matrix artifact it was derived from is kept as a reference only.

  • Where a record carries more than one kind of data, it is listed once per kind. For example, JobRecord is listed as B for variables and as C for errorMessage, and MessageRecord as B for variables and as D for correlationKey.
  • JobRecord.customHeaders is not listed as variable-carrying.
  • ClusterVariableRecord is out of scope. Cluster variables are not process variables and are not protected.
  • Categories C and D are listed so that the gap is visible, but they are out of scope (L3).
  • Records that wrap other commands (COMMAND_DISTRIBUTION, BUFFERED_COMMAND) and AGENT_HISTORY are tracked as uncategorized in the matrix. The variable history (#3517) is listed there too. It stores the new value of each variable change and redacts it only when the command explicitly carries protection modes.

Priorities

  • Must have: BUFFERED_COMMAND, because it wraps a command that can carry protected variables.
  • Nice to have: COMMAND_DISTRIBUTION and AGENT_HISTORY.

Appendix A is maintained as the source of truth. A new record type or field that can carry a value is added there before it is protected.

Guarantees​

For values written after a variable was declared sensitive, in the scope delivered by the milestones above:

  1. Variables are still exported, with a redacted value (categories A and B only). A redacted variable keeps being exported to secondary storage (Elasticsearch, OpenSearch or RDBMS), but its real value is not written there.
  2. The value is not visible in the UI. A redacted variable is still listed. Operate and Tasklist show [REDACTED] instead of its value.
  3. The value is not visible in the API reads served from secondary storage, that is the search and get endpoints (for example POST /variables/search, GET /variables/{variableKey}, user task variables). A redacted variable is still returned, with its value redacted. Endpoints served from primary storage, such as job activation, return the plain value (L2).

Known limitations​

  • L1. No redaction of nested variables. A sensitive field inside an object variable is not addressed. The whole variable is protected or none of it.
  • L2. Primary storage is not protected. The engine needs the real value, so the Raft log, RocksDB, snapshots, backups and every API served from primary storage (job activation, process instance result, scoped expression evaluation) carry the plain value. Redaction protects reads that observe a process (search, Operate, Tasklist), not reads that execute a step. Anyone able to register a worker for a task still receives the value of the variables it uses. This is intentional.
  • L3. Only categories A and B are supported. Category C free text that can quote a value (error messages, warnings, rejection reasons) and category D derived values (decision inputs and outputs, copies, FEEL transformations, correlation keys, multi-instance values) are not protected. A derived value, for example the result of a FEEL expression that reads a protected variable, is protected only if the variable it is written to is also explicitly marked as protected. The matrix still lists these records so the gap is visible.
  • L4. No backfill. A declaration protects values written after it is made. Values already exported stay readable, so turning redaction on does not clean up existing data.
  • L5. Tasklist forms with redacted initial variables cannot be displayed.
  • L6. Search by value finds nothing. A redacted value cannot be matched by a variable-value filter, because the stored value is an empty string.
  • L7. Correlation keys are persisted by the Camunda and RDBMS exporters from the message subscription records today. They are often derived from a variable (see L3).
  • L8. The variable history keeps each change as it was protected at the time. A change written without protection stays readable. A change written with protection is redacted. Adding protection later does not rewrite earlier entries, and removing it needs an explicit action, not a missing field. Sensitive variables must be protected when they are created, otherwise their earlier values stay visible in the history (#3517).
  • L9. The engine redacts only what a command explicitly marks as protected. A command without protection modes is processed as though its variables were not protected, so no redaction is applied to it.

Appendix B: Option B, configurable name patterns​

Option B is not the decision (D2). It is kept here so that the ADR can be revised quickly if the customer prefers the smaller scope.

How option B works​

A pattern is configured for the cluster. It can be a prefix or a suffix, whichever the customer prefers, for example redact_.*. A variable whose name matches the pattern is redacted. Option B ends in the same redaction step (D7) and the same redacted result (D8) as option A. Search results still return protectionModes (D4). It reuses D6 to D8.

Not decided:

  • How option B marks the exported record. The proposal is to set the same REDACT metadata as in D8, so that the read APIs and UI behave identically.
  • Where the patterns are configured.

Option B in the UI​

The examples use the prefix redact_. A suffix works the same way. A variable whose name matches the pattern is redacted, so the Modeler needs no extra control: the user only names the variable. In the Modeler, a mapping such as redact_pan = redact_cardNumber produces a redacted local variable, and an output mapping to redact_networkToken produces a redacted process variable. Operate and Tasklist show [REDACTED] for redact_cardNumber, while amount shows its value. The final Modeler design is still to be confirmed.

Appendix C: Alternatives considered​

  • Engine-side destruction before the append (D1).
  • Redaction by exporter handler or exporter serialization hook (D6).
  • Variable-name prefix or suffix patterns (option B): not chosen, described in Appendix B. On its own it cannot express combined modes without further naming conventions, forces whatever reads the variable (workers, expressions) to use the prefixed name, and a typo silently disables protection.
  • Returning null as the redacted value: rejected for D8, it makes value nullable, a breaking change for generated clients that hits every consumer, not only those who enable redaction.
  • Returning a "REDACTED" sentinel as the redacted value: rejected for D8, it can collide with a real value and duplicates protectionModes.
  • Omitting the redacted variable or its value from the response: rejected for D8, it breaks the required value and hides that the variable exists, and pagination and totalItems would no longer match what Operate shows.
  • Suppressing a redacted variable for Optimize instead of sending the marker: rejected for D7 because it needs a second redaction behavior and makes Optimize disagree with Operate about what exists. A marker keeps instances visible and countable in reports.
