# Per-physical-tenant secondary-storage schema initialization: isolated, retried, non-fatal per tenant

**DRI**: Houssain Barouni

**Status**: Proposed (8.10)

**Deciders**
- Houssain Barouni
- Lena Schönburg

**Purpose**: Define how a physical tenant's secondary-storage schema is initialized when one orchestration cluster hosts several tenants: what startup waits for, what "ready" asserts, and what happens to a tenant whose storage cannot be reached.

**Audience**: Engineers working on the broker/gateway distribution, the schema managers and the data layer, and operators of multi-tenant clusters.

## Context

Schema initialization today runs every physical tenant sequentially on a single thread, with an unbounded retry *inside* each attempt, and takes one of two startup paths. With an embedded gateway the whole Spring context refresh blocks until every tenant has been initialized; without one, initialization runs entirely in the background and startup never waits. A first tenant whose storage is unreachable therefore starves every tenant behind it without ever throwing, and on the gateway path it withholds the entire node — for every tenant — for as long as the outage lasts. Any failure that does escape aborts the context and takes the node down.

The two consumers of an initialized schema already tolerate a tenant that is not initialized, each per tenant: the exporter verifies the schema when opening and its director retries opening indefinitely with backoff, per partition; the v2 REST endpoints that need secondary storage are rejected per request, with 503 and a `Retry-After` hint, for a degraded tenant. Neither needs startup to hold the context refresh.

Startup nevertheless still holds it, for a different reason. The node's listening socket is the only admission control that works without an orchestrator, and it is coarse but decisive: while the port is closed no client reaches the node at all. That matters during the ordinary case where nothing is wrong and initialization is simply not finished yet — a browser pointed at a node in that state loads the webapp and receives 503 from every endpoint that needs secondary storage, and its login misbehaves rather than merely erroring, because the Elasticsearch-backed session write is skipped while the tenant is uninitialized. Opening the port early converts a few seconds of waiting into a broken product.

The design therefore has to separate two situations that look identical to a readiness signal alone. In the first, storage is healthy and initialization is progressing: nothing is wrong, the wait is bounded by the work, and the port should stay shut. In the second, a tenant's storage cannot be reached: the wait is unbounded, the node can still serve every other tenant, and holding the port serves nobody. The outcome is per-tenant isolation with a startup barrier that discriminates between the two.

## Decision

**D1. Each physical tenant's schema initializes independently, and no single tenant's failure aborts the application context.**
One task per tenant, run concurrently, each retrying in the background until it succeeds. A tenant whose storage fails degrades itself and nothing else: as long as the node can serve some tenant, or could still come to serve one, it stays up. Startup aborts only in the one case where neither is true and never will be — every tenant terminal (D3).

**D2. Only a node with an HTTP gateway holds startup. A node without one does not wait at all.**
The barrier exists to protect the HTTP surface — the webapp, the persistent session store, the v2 REST endpoints. A node without an HTTP gateway serves none of them: its exporter already retries per partition and no consumer of its startup benefits from waiting. The condition is the one `HealthConfigurationInitializer` already uses to decide whether the schema readiness indicator joins the readiness group, so there is a single condition rather than two that can drift.

**D3. The barrier is released once every tenant has settled and either one tenant is serviceable or none is still trying — except when nothing is serviceable because every tenant failed terminally, which aborts startup.**
A tenant has *settled* once it has either initialized or failed at least once. Requiring a serviceable tenant on top of that is what keeps a node whose storage is merely still starting from opening its port a second later and serving 503s: the first attempt fails within the storage client's connect timeout, but the barrier holds until the tenant actually initializes. Requiring that only when some tenant can still make progress is what keeps the barrier from waiting on a condition nothing can satisfy — every tenant terminal, or every retry budget exhausted, leaves no task running to ever produce a serviceable tenant, and startup would otherwise hang silently and forever.

Releasing is the right answer to "nothing is serviceable" only where the node might still be worth running. Every tenant terminal is not that case: it is a diagnosis, made by D6's classification, that no amount of waiting will change the outcome without operator action. A node released into that state serves nothing, becomes ready never, and — because the barrier governs the HTTP surface and not the broker — goes on exporting into the schema the classification just refused. The exporter's own guard does not catch it: `CamundaExporter.open` refuses to open on `isSchemaReadyForUse`, which checks that indices, templates, mappings and aliases are as the code describes, and not the version recorded in the metadata index that a version incompatibility is raised from. A schema whose shape matches but whose version this node must not migrate therefore passes it. Aborting states the same conclusion in the one channel every operator and orchestrator already watches, and it is what a node does today. The other ways a tenant can stop trying are not diagnoses: an exhausted retry budget is an operator's configured give-up, and a task that could not be run at all is our defect. Neither justifies taking the node down, so both keep the not-ready release.

The cases the rule separates:

|                             situation                              |                                                                              behaviour                                                                               |
|--------------------------------------------------------------------|----------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| storage healthy, initialization or migration in progress           | held until every tenant completes — a rolling-upgrade node stays out of the load balancer until all of its tenants have migrated                                     |
| one tenant's storage unreachable, another serviceable              | released once the unreachable tenant has failed an attempt and the serviceable one is ready; the degraded tenant keeps retrying in the background                    |
| one tenant failed, one serviceable, one still in its first attempt | held until the third tenant settles too — settling is required of every tenant, and a tenant yet to produce an outcome is indistinguishable from one still migrating |
| no tenant serviceable and every tenant still retrying              | held, retrying, exactly as a single-tenant node does today                                                                                                           |
| no tenant serviceable and every tenant terminal                    | startup aborts — the context refresh fails and the node exits non-zero, as it does today                                                                             |
| no tenant serviceable and none still trying, for any other reason  | released; the node comes up not-ready, with logs, metrics and actuator available for diagnosis                                                                       |

The abort is part of the barrier, so by D2 it reaches only the nodes that hold one. A node without an HTTP gateway does not evaluate the rule at all and stays up with every tenant degraded, which is what it does today and what its exporter's per-partition retry expects.

**D4. A tenant's readiness is a one-way latch asserting that the schema described in the source code was applied — not that its storage is currently reachable.**
Initialization performs real reads and writes against the tenant's own indices, so success is authenticated, writable, tenant-scoped proof. The latch never reverts, and probes consequently do not observe a storage outage that begins after initialization has succeeded. Detecting runtime degradation is a separate mechanism with its own requirements, and the readiness interface is the seam through which it would later be supplied.

**D5. Node readiness stays "at least one serviceable tenant", and no storage-liveness check participates in it.**
Unchanged from [001](001-physical-tenant-health-status-topology.md) D2. Adding "every tenant settled" to the probe would be redundant: D3 already guarantees it before the context finishes refreshing on the nodes that expose the indicator. This ADR additionally rules out gating initialization, and therefore readiness, on a storage cluster-health check.

Two consequences of keeping "at least one" are worth stating outright. A node that serves some tenants and not others reports ready, and traffic for a tenant that is not serviceable is refused per request — `503` with `Retry-After`, on the tenant's own requests only — rather than by withholding the node from every tenant it *can* serve. And where D3 releases the barrier with nothing serviceable at all, the probe reports not ready for the life of the pod: the latch is one-way per tenant and no task remains to set it, so the node needs operator action either way. That is the state D3 aborts on when it is a diagnosis, and reports through readiness when it is not.

**D6. Failure classification decides whether a tenant keeps retrying, and through that whether the barrier releases, aborts, or holds.**
A failure that retrying cannot repair stops that tenant's loop and is logged at ERROR; everything else is retried and logged at WARN. The classification is therefore not observational at all, and each way of getting it wrong costs something different. Calling a terminal failure retryable holds a gateway node at the barrier indefinitely. Calling a retryable failure terminal costs one degraded tenant on a node that has others — but on a node whose tenants are *all* misclassified that way, and a single-tenant node is the common instance of that, it converts an outage the node would have retried through into a crash loop. That last cost is new with D3's abort and it is the largest of the three, so the bar for calling a failure terminal is "certainly not repairable without operator action", and conservatism is the safe direction throughout.

**D7. One storage-agnostic per-tenant initialization component owns retry, state and observability; each schema manager exposes a single-attempt operation.**
Bounded transient retries stay inside an attempt, where they already live. The unbounded outer loop, the barrier, per-tenant state and the transition logs live in the shared component, which both Elasticsearch/OpenSearch and RDBMS ([#54299](https://github.com/camunda/camunda/issues/54299)) use.

**D8. Per-tenant degradation is surfaced through transition logs and the existing binary per-tenant readiness gauge; no new state metric or state vocabulary is introduced.**
This satisfies 001 D2's requirement that degraded state be visible per tenant in logs and in metrics. A tenant that will not recover without operator action is distinguished in the logs, not by a metric value; the operationally decisive alert — a tenant not ready for longer than some period — is already expressible over the existing gauge.

## Alternatives considered

- **Block startup until every tenant is ready.** Today's gateway behaviour generalized to many tenants. Rejected: one tenant's storage outage then withholds the entire node indefinitely, which is the defect this ADR exists to remove.
- **No barrier at all; let the readiness probe govern admission.** Rejected: readiness only withholds traffic where something consumes it. A node reached directly — a browser against a local or single-node deployment, a load balancer configured with a TCP check — is served a webapp whose every secondary-storage call fails and whose session store silently refuses writes. The socket is the only admission control that holds in every environment, and the case it protects is the ordinary one where nothing is wrong.
- **Release each tenant's share of the barrier on its first outcome alone.** Rejected: the Elasticsearch client's default connect timeout is one second, so a node started alongside its storage releases the barrier a second in and then serves 503s for as long as the storage takes to boot. The same knife-edge admits a rolling-upgrade node on a single 30-second socket timeout during a long migration.
- **Come up not-ready when every tenant is terminal, rather than aborting.** Rejected, having first been decided: it makes actuator, metrics and logs reachable, which a crashed node's actuator is not. But nothing about the state is transient, so the endpoints answer the same question forever, and the two properties that argument leans on do not hold. The failure is already in the container log before the abort, which survives the restart, so the diagnosis is not actually lost. And a node released this way still runs its broker and its exporter against the schema the classification refused, where aborting stops both — the barrier withholds the HTTP surface, never the engine. A permanently not-ready pod is the same outage as a crash loop, reported through a channel that fewer alerts watch.
- **Abort on every node, gateway or not.** Rejected for this change, and closer to what a node does today, since aborting the context never depended on the gateway. It would need asynchronous self-termination after the context has already refreshed, because a node without a gateway never reaches the barrier — a heavier mechanism, with a new failure mode, for a node whose exporter is designed to retry per partition indefinitely. Reconsider if a degraded exporter on a broker-only node proves worse in practice than a restart loop.
- **Bound the wait with a grace period before a failing tenant settles, or with a plain timeout.** Rejected: the barrier is held by the slowest tenant to settle, so a grace period changes the outcome only when the *failing* tenant is the last one — and in exactly that case waiting for a serviceable tenant is both simpler and strictly better, because it waits for the condition that actually matters instead of for a clock. A plain timeout is worse still: it abandons a legitimate long migration and breaks the rolling-upgrade guarantee outright.
- **Derive readiness from live per-tenant storage health.** Rejected: acting on a probe affects every tenant on the node, so a live check for one tenant can withhold traffic for all of them, and it reproduces the restart cascades caused by the module-specific search-engine indicators.
- **Gate initialization on a cluster-wide storage health check.** Rejected: a cluster-wide answer is identical for every tenant, so one tenant's unassigned shards would degrade all tenants — the coupling this work removes — and it makes an additional storage privilege a hard startup requirement.
- **Derive readiness from the schema version recorded in storage.** Deferred, not rejected: compare the version stored in the tenant's metadata index against the running version, treat "behind" as still migrating, and ignore a tenant whose storage cannot be read. It is more truthful than the latch, because it is satisfied by any node's migration and re-evaluated continuously, which would close the residual noted below. It also carries three requirements that make it a larger change than this one: ignoring unreadable tenants must be a conjunct with D5 and not a replacement, or a node whose storage is entirely down advertises itself as ready; the same predicate has to back request-time rejection too, or the node reports ready while rejecting every request; and the result must be latched once confirmed, or every probe costs a read per tenant and a flapping cluster flaps readiness. Those requirements make it the natural shape for the readiness-indicator unification in [#51861](https://github.com/camunda/camunda/issues/51861), which it would also subsume.

## Consequences

- A rolling upgrade takes as long as the slowest tenant's migration, because the upgraded node is withheld until every tenant has settled. In exchange no tenant is served 503s by a node that has not migrated it yet.
- A single-tenant node whose storage is unreachable behaves exactly as it does today: startup is held, initialization retries, and nothing is served. 001 D2's "single-tenant clusters keep today's operational behavior" is therefore met rather than refined.
- A tenant that fails once during a rolling upgrade has settled, so the node can be admitted while that tenant is still retrying its migration, and its requests are rejected by a node that has not migrated it. Closing this window is what the deferred storage-version readiness above would buy.
- A node whose tenants are all terminally misconfigured aborts and crash-loops, as it does today. What changes is that one such tenant among several no longer does: the node comes up and serves the rest. The failure that caused the abort is logged at ERROR before the exit, and the exception that aborts the context names every tenant.
- A node whose tenants have all stopped trying for a reason that is *not* a terminal classification — every retry budget exhausted, or a task that could not be started — comes up not-ready instead, where it previously aborted. This is the one direction in which a node that used to crash now stays up, and it is deliberate: neither cause is a diagnosis that the deployment is wrong.
- While the barrier is held the management context has not started, so logs are the only startup diagnostic. On a node whose storage is unreachable and whose tenants are all still retrying, that window lasts as long as the outage — unchanged from today, and the reason D3 releases as soon as any tenant is serviceable.
- A node without an HTTP gateway is unaffected in every respect; its schema initialization is asynchronous as it is today.
- No probe observes a storage outage that begins after a tenant was initialized. Requests to that tenant fail on the read path rather than being rejected as degraded.
- A tenant that stays degraded never advances its exporter position, so the logs of its partitions keep growing. Degradation has a disk cost with a long fuse.
- Mapping validation is classified retryable, so a node whose only tenant has an index the running version cannot migrate is held at startup indefinitely, as it is today. Splitting that failure — a changed field type is unrepairable, an ambiguous mapping is what a peer node mid-migration transiently looks like — and classifying only the first as terminal is tracked separately.
- Until the module-specific search-engine readiness indicators are replaced by the unified indicator ([#51861](https://github.com/camunda/camunda/issues/51861)), a degraded *default* tenant still fails the readiness group, so isolation is observable only for non-default tenants. This ADR assumes that replacement lands and does not depend on it.
- The shared component must be able to express a tenant that is terminal from birth, because RDBMS builds each tenant's object graph once at startup and never rebuilds it lazily.
