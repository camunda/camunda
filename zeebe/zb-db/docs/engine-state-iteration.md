# Column family iteration in the engine

An inventory of every place where the engine iterates a column family, grouped by when the code
runs in production. It backs fact 3 in [write-behind-cache-design.md](write-behind-cache-design.md).

## How this list was built

- **Scope:** `zeebe/engine/src/main`. A call site is a call to `whileEqualPrefix`, `whileTrue`,
  `whileTrueReverse`, `forEach`, `forEachKey`, `isEmpty`, `count` or `countEqualPrefix` on a field or
  parameter typed `ColumnFamily`. All 137 call sites live under `engine/state`, in 47 classes.
- **Production use:** callers were followed up the call graph, by method name and the declared type
  of the receiver, until the first caller outside `engine/state`. That caller decides the category.
  Generic names (`forEach`, `isEmpty`, `remove`, `getAll`, `cleanUp`, `onRecovered`) were checked by
  hand. Every behavior and helper counted as production has callers itself.
- **Limits:** this is static analysis of the source text. Line numbers are left out because they go
  stale; search for `Class#method`.
- **Correction:** the design doc said "about 219 iteration call sites in 35 state classes". That
  figure came from a plain text search that also matched `List#forEach`, `String#isEmpty`,
  `Stream#count` and similar. The real number is 137.

- **Prefix scan:** Visits every entry under a key prefix, usually one instance or scope.
- **Prefix, first match:** Prefix scan that stops at the first hit (`has…`, `getFirst…`, `peek…`).
- **Prefix count:** `countEqualPrefix`.
- **Full scan:** Visits the whole column family, sometimes stopping early.
- **Paged scan:** `whileTrue(startAtKey, …)`: resumes after the last key of the previous page.
- **Ordered scan up to now:** Time-sorted column family, read from the start until the first entry that is not due yet.
- **First match from the start:** Reads from the start of the column family until the first hit.
- **Column family empty?:** `isEmpty`: reads the first entry of the column family.
- **Full count:** `count`: visits every key of the column family.

### What this means for the write-behind design

- **Most iteration on the command path is narrow.** 64 of the 79 call sites that run per command
  read the entries of a single instance, scope or key prefix. The DirtyIndex copy that each iterator
  takes (§4.5) stays small for these.
- **Nine full scans run per command.** Each copies every dirty entry of its column family, so measure
  them in Phase 3:
  - `DbGlobalListenersState#getCurrentConfig`, in user task appliers
  - `DbJobMetricsState#cleanUp` (two scans), in an applier
  - `DbMappingRuleState#getAll`, on authorization checks, with no cache in front
  - `DbGroupState#scanAllGroupIdsByName`, on a group cache miss
  - `DbBannedInstanceState#getBannedProcessInstanceKeys`
  - `DbTenantState#forEachTenant`
  - `DbDistributionState#foreachRetriableDistribution`
  - `VersionManager#forEachResource`
- **Merged iteration is also on the replay path.** 19 call sites run inside event appliers, which
  replay on followers and on every restart.
- **Scheduled scans re-read the newest entries.** The scans for due timers, job deadlines and
  backoffs, message TTL and dedup expiry read time-sorted column families from the start. Recently
  written deadlines sit in the DirtyIndex, so every run copies the dirty part of the column family.
- **The engine never iterates in reverse.** `whileTrueReverse` is used only by backup state (two
  call sites, see below). The merge iterator still needs reverse support, but not for processing.
- **12 call sites never run in production** (test-only or unused).
