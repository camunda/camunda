# DMN benchmark: Camunda 8.9.24 vs 8.9.28 vs 8.10.9 (small, medium and large DMN)

Date: 2026-11-05 (Batches A, B) and 2026-11-10 (Batch C) · Branch: [`ajanoni/dmn-8.10-benchmark`](https://github.com/camunda/camunda/tree/ajanoni/dmn-8.10-benchmark)
· Based on [#65841](https://github.com/camunda/camunda/pull/65841) (`dmn-large` k6 scenario)

## TL;DR

**What is tested:** the same DMN decision graph, at the same fixed evaluation rate, on released
`camunda/camunda` images with 3 brokers each. The main comparison is **8.9.28 vs 8.10.9** (3 runs
each). **8.9.24**, the last 8.9 release without any of the DMN performance changes, is a third
reference (Batch C, 1 run). A JRE 21 build of 8.10.9 separates the Java version from the code. The
tests measure resource cost and latency at a fixed load, not maximum throughput. See
[What is tested](#what-is-tested).

At the same DMN and evaluation rate, 8.10.9 spends far less engine time and broker CPU per decision
evaluation than 8.9.28. The gap grows with the size of the model. Each value is the mean of 3 runs,
with the min–max range in brackets.

|     DMN size     | Engine time per evaluation (ms) |   Broker CPU per evaluation¹ (CPU-ms) | k6 client latency p50 (ms) |
|------------------|--------------------------------:|--------------------------------------:|---------------------------:|
| Small (0.25 MiB) |            9.8 → 2.4 (**−75%**) |    30 [29–31] → 19 [18–20] (**−37%**) |     20.4 → 12.9 (**−37%**) |
| Medium (6 MiB)   |           70.0 → 4.9 (**−93%**) |   97 [89–110] → 27 [26–30] (**−72%**) |     84.7 → 16.9 (**−80%**) |
| Large (48 MiB)   |           518 → 10.1 (**−98%**) | 758 [744–783] → 39 [35–45] (**−95%**) |      496 → 23.8 (**−95%**) |

¹ Total CPU of the 3 brokers, minus the idle baseline, divided by the evaluation rate.

- **The gain comes from the DMN engine, not from the Java version.** 8.9.28 runs on JRE 21 and 8.10.9 on
  JRE 25 with compact object headers. 8.10.9 rebuilt on 8.9.28's JRE 21 base has the same engine
  time per evaluation as 8.10.9. Its CPU, memory and GC figures move, but by far less than the gap
  to 8.9.28 (see [Java isolation](#java-isolation)).
- **Every evaluation succeeded.** k6 sent 72,000 / 10,800 / 3,590–3,600 evaluations per 30-min window
  (small / medium / large) in every run. None returned a non-200 status and none returned a wrong
  result. No broker restarted.
- **Flamegraphs** show where the saving comes from. On 8.9.28 the large DMN spends 0.93 cores in
  dmn-scala / FEEL evaluation, dominated by Scala immutable map building. On 8.10.9 it spends
  0.018 cores.
- **Queueing and export delays shrink as a side effect.** With 8.9.28, a 0.5 s evaluation of the
  large DMN blocks its partition, so 14% of commands wait more than 25 ms in the queue. On 8.10.9 it
  is 0.01%. One of the three 8.10.9 small-DMN runs had an export stall (6.1 s mean export pickup
  delay) that no 8.9.28 run had. It is not explained yet (see [Caveats](#caveats)).
- **Memory:** broker RSS is lower on 8.10.9 (−40%, −35%, −13%), with or without JRE 25. This
  benchmark cannot tell whether 8.10.9 retains less heap for the large model: the live-heap gauge
  is not reliable when, as on 8.10.9, the JVM rarely collects garbage.
- **Exporter CPU** (profiles) falls with the linear decision export: on the small DMN at 40
  evaluations/s the exporter uses 2.64 cores on 8.9.24, 0.15 on 8.9.28 and 0.09–0.10 on 8.10.9
  (−96% from 8.9.24 to 8.10.9). See [Exporter CPU](#exporter-cpu-across-the-three-versions).
- **Against 8.9.24, the last release with none of these changes,** the gap is wider still: broker
  CPU per evaluation drops by 82%, 90% and 99%, and the large DMN takes 1.4 s per evaluation on
  8.9.24 (518 ms on 8.9.28). See [Batch C](#batch-c-baseline-without-any-of-the-changes-8924).

## Purpose

These recent DMN changes on `stable/8.10` should lower the cost of evaluating and exporting
decisions, especially for large decision graphs:

|                                                                              Change                                                                              | In 8.10.9 | In 8.9.28  |
|------------------------------------------------------------------------------------------------------------------------------------------------------------------|:---------:|:----------:|
| dmn-scala 1.12.6 ([#67857](https://github.com/camunda/camunda/pull/67857))                                                                                       |     ✅     | ❌ (1.11.4) |
| Cached DMNs release their parsed XML model ([#67792](https://github.com/camunda/camunda/pull/67792))                                                             |     ✅     |     ❌      |
| Keep decision export cost linear ([#67998](https://github.com/camunda/camunda/pull/67998), 8.9 backport [#67997](https://github.com/camunda/camunda/pull/67997)) |     ✅     |     ✅      |
| Size exported records instead of Kryo ([#67883](https://github.com/camunda/camunda/pull/67883))                                                                  |     ✅     |     ❌      |

The benchmark compares the **latest released images** of both minors, `camunda/camunda:8.9.28`
and `camunda/camunda:8.10.9`. The two minors also differ in other engine, exporter and Helm
chart changes, and in the Java runtime (see [Images and JVM](#images-and-jvm)).

## Setup

Batch A ran 6 load tests (2 versions × 3 DMN sizes). Batch B ran 16 more: two repeats of each,
two JRE 21 isolation runs and two idle baselines. Batch C ran 6 more on 2026-11-10: 8.9.24 and a
fresh 8.10.9 control, each at three sizes. Each batch ran in parallel on the benchmark GKE
cluster, so all tests in a batch share the same window and node pool. Every test used the
`dmn-large` scenario, deployed through the
[`camunda-load-test.yml`](../../../.github/workflows/camunda-load-test.yml) workflow.

|         Item          |                                                              Value                                                              |
|-----------------------|---------------------------------------------------------------------------------------------------------------------------------|
| Orchestration cluster | 3 brokers, 6 partitions, replication factor 3, partition leaders rebalanced                                                     |
| Broker resources      | 3 CPU request and limit, 10 GiB memory limit, `-XX:MaxRAMPercentage=60` (6 GiB max heap), `cpuThreadCount=3`, `ioThreadCount=3` |
| Broker disk           | 64 GiB SSD PVC                                                                                                                  |
| Message size          | `camunda.cluster.network.max-message-size=128MB`, 64 MB multipart limit                                                         |
| Secondary storage     | Elasticsearch (ECK), Camunda exporter                                                                                           |
| Optimize              | disabled                                                                                                                        |
| Nodes                 | `stable-vms=true` (n2-standard-4, non-preemptible). One broker per node, because a broker requests 3 of the 4 vCPUs             |
| Helm setup            | `load-tests/setup/stable-89` for 8.9.28, `load-tests/setup/stable-810` for 8.10.9                                               |
| Platform values       | `values/camunda-platform-values-defaults.yaml` + `values/camunda-platform-values-dmn-large.yaml` + Elasticsearch values         |
| Workload              | k6 `dmn-large` test only (no BPMN starter or workers), k6 runner 1 CPU / 2 GiB                                                  |

To run the `dmn-large` scenario on `stable-810` and `stable-89`, this branch adds the overlay to
both setups and gives the k6 client the `DECISION_DEFINITION` permissions it needs.

## Input

The k6 init container builds the DMN with
[`generate_tariff_dmn.py`](../../setup/charts/load-test-setup/k6/generators/generate_tariff_dmn.py).
The output is deterministic, so both versions evaluated byte-identical models. Every model has
the same shape: a freight-tariff decision graph with 12 decisions, three large FIRST-hit tables,
FEEL combiner tables and one top decision that requires the whole graph. Only the number of rules
changes with the size.

|  Size  | `DMN_SIZE_MIB` | File size | Rules | Test vectors | Rate (`DMN_RATE`) |
|--------|---------------:|----------:|------:|-------------:|------------------:|
| Small  |           0.25 |  0.25 MiB |    56 |        3,044 |  40 evaluations/s |
| Medium |              6 |   6.0 MiB |   972 |        3,960 |   6 evaluations/s |
| Large  |             48 |  48.0 MiB | 8,479 |       11,467 |   2 evaluations/s |

- The rate goes down as the size goes up, so that both versions stay below saturation. The
  benchmark measures **resource cost and latency at a fixed load**, not maximum throughput.
  Because each size runs at a different rate, compare the two versions within a size. Do not
  compare across sizes.
- Executor: k6 `ramping-arrival-rate`, `DMN_RAMP_UP=10m`, `DMN_PRE_ALLOCATED_VUS=40`.
- The default `DMN_DEPTH_MIX` cycles through the test vectors: targeted vectors (one per
  reachable rule), random, payload-like and fall-through vectors. The order is shuffled with a fixed
  seed, so both versions get the same sequence. A 30-minute window covers every vector of the small
  and medium models: 72,000 evaluations for 3,044 vectors, and 10,800 for 3,960. It covers only a
  sample of the large model: 3,600 of 11,467 vectors.
- Each test deploys the DMN once, then evaluates the top decision through
  `POST /v2/decision-definitions/evaluation`.

### Metrics

Metrics come from the benchmark Prometheus. They were collected with
[`camunda-load-test-metrics.yaml`](../../../.github/workflows/camunda-load-test-metrics.yaml)
(`duration-seconds=1800`, `at=<window end>`), which runs `loadtestctl report`. Batch A also used the
default query set ([`report-queries.yaml`](../../loadtestctl/src/loadtestctl/report/report-queries.yaml)).
All the numbers below come from an extended query set, stored with the results as
[`extra-queries.yaml`](2026-11-dmn-8.9-vs-8.10-results/extra-queries.yaml).

|            Metric             |                                                                                What it measures                                                                                 |
|-------------------------------|---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| k6 evaluations / non-200      | `k6_http_reqs_total` for evaluation requests, by HTTP status                                                                                                                    |
| k6 client latency p50 / p99   | `k6_http_req_duration` (native histogram) of evaluation requests: the full round trip seen by the client                                                                        |
| Engine time per evaluation    | Mean of `zeebe_stream_processor_processing_duration` for `DECISION_EVALUATION` commands: the time the engine spends processing one evaluation command                           |
| Broker CPU (total, busiest)   | Average CPU of the 3 broker pods, summed or of the busiest pod (`container_cpu_usage_seconds_total`)                                                                            |
| Broker CPU per evaluation     | (total broker CPU − idle baseline of the same version) ÷ evaluation rate. 8.9.28 idle: 0.21 cores; 8.10.9 idle: 0.18 cores                                                      |
| **Command queue wait**        | `zeebe_stream_processor_latency`: time from a command being written to the log until the stream processor *starts* processing it. This is a queueing delay, not evaluation time |
| **Export pickup delay**       | `zeebe_exporting_latency`: time from a record being written until the exporter picks it up                                                                                      |
| GC pause fraction / max pause | `jvm_gc_pause_seconds`: share of wall time in stop-the-world pauses on the worst broker, and the longest pause                                                                  |
| Heap live after GC            | `jvm_gc_live_data_size_bytes`, highest value of any broker in the window. It is updated only after a collection, so it lags when collections are rare                           |
| RSS                           | Average container RSS of the broker with the highest RSS                                                                                                                        |
| ES index operations           | Increase of Elasticsearch indexed documents in the window                                                                                                                       |

The Zeebe latency histograms use the bucket bounds 5, 10, 25, 50, 75, 100, 250, 500, 750 ms, 1 s, …
(`MicrometerUtil`). Percentiles that fall inside one bucket are interpolated and not precise. The
results therefore show the **mean** and the **share of records at or below 25 ms**, both computed
exactly from `_sum`, `_count` and bucket counts. Batch A's earlier report showed p50/p99 values for
these histograms. They are no longer used.

### Profiles

On the Batch A clusters, shortly after their window (about 21:40 UTC), async-profiler captured 300 s of CPU, wall-clock and allocation profiles on all

([`profile-load-test.yml`](../../../.github/workflows/profile-load-test.yml)). Each CPU sample is

## Interpretation

- **Engine cost per evaluation.** Engine time per evaluation drops by 75%, 93% and 98%, and CPU per
  evaluation by 37%, 72% and 95%. The profiles place the saving in dmn-scala / FEEL evaluation.
  That is consistent with the dmn-scala 1.11.4 → 1.12.6 upgrade (#67857), the largest DMN-specific
  change between the two images. This benchmark does not separate it from other 8.9 → 8.10 changes,
  because no image of 8.10.9 with dmn-scala 1.11.4 was tested.
- **Small vs large gains.** Do not compare the gains across sizes: each size runs at a different
  rate, and in the small runs a larger share of CPU goes to exporting and the REST path. The per-size
  gains are robust: the ranges of the two versions never overlap.
- **Queue wait and export pickup.** These are not evaluation times. They grow on 8.9.28 because one
  slow evaluation (about 0.5 s for the large DMN) holds its partition's stream processor. Commands
  behind it, and the exporter waiting for those records, have to wait. On 8.10.9, evaluations take
  about 10 ms, so the delays stay close to the 8.10.9 idle baseline (1.2 ms queue wait, 4.1 ms export
  pickup). In Batch A, the export and processing backlogs average less than one record in every run,
  so neither version builds a backlog at these rates.
- **Throughput.** Both versions served exactly the configured rate in every run, with no dropped
  iterations and no backpressure. Neither version was saturated. In Batch A, 8.10.9 processed 0.3–0.6 records/s more than
  8.9.28 at every size. After subtracting the evaluations, both versions have a constant background
  record rate: about 3.4–3.8 records/s on 8.9.28 and 4.1 on 8.10.9. The difference comes from this
  background rate, not from 8.9.28 falling behind.
- **Memory.** Broker RSS is lower on 8.10.9: −40% small, −35% medium, −13% large. The JRE 21 build
  of 8.10.9 shows the same or lower RSS, so the reduction is not caused by JRE 25 or compact headers.
  For the large DMN, both versions commit the whole 6 GiB heap, so RSS mostly reflects committed
  heap.
- **Live heap.** For the large DMN, live heap after GC reads higher on 8.10.9: 3.39 [3.00–4.13] GiB
  against 2.40 [1.99–2.70] GiB, and the ranges do not overlap. This does not show that 8.10.9
  retains more memory. The gauge reports what was left after the most recent collection, and
  8.10.9 collects about 25 times less often (0.006–0.010 pauses/s on the busiest broker, against
  0.18–0.21 on 8.9.28), so its last value still includes garbage. The idle clusters show the same
  effect (2.0 GiB on 8.10.9, 0.14 GiB on 8.9.28), and the JRE 21 build of 8.10.9 reads 1.68 GiB.
  Retained heap needs a heap histogram or a forced full GC, which this benchmark did not take. It
  therefore shows **no measurable effect, in either direction, of releasing the parsed XML model**
  (#67792). For small and medium models, live heap is the same or lower on 8.10.9.
- **GC.** The share of time in GC pauses drops on 8.10.9 for every size: 0.89% → 0.40% (small),
  0.23% → 0.04% (medium) and 0.38% → 0.06% (large). The longest pause drops only for the large
  DMN, from 189–315 ms to 115–148 ms, and to 17 ms on the JRE 21 build. For small and medium it is
  slightly higher on 8.10.9 (16–20 → 18–25 ms, 13–31 → 19–45 ms), within the range of a single
  young collection. The lower pause share is consistent with the lower allocation in the evaluation
  path seen in the profiles.
- **Elasticsearch.** 8.10.9 performs about 37% fewer index operations for the same number of
  evaluations, at every size. This means it writes fewer documents per evaluation. Possible
  reasons are exporter and schema changes between the two minors, including how exported records are
  sized (#67883). ES CPU was low in all runs.

## Caveats

- **Version comparison, not one commit.** The benchmark compares two released images. The
  DMN-specific differences between them are dmn-scala 1.11.4 → 1.12.6 (#67857), the release of the
  parsed XML model (#67792) and the sizing of exported records without Kryo (#67883). The 8.9 line
  already has the linear-export fix (#67997). Other engine, exporter and chart changes between the
  minors are also included.
- **JRE 21 isolation is one run per size,** and the custom image comes from the CI build pipeline,
  not the release pipeline. Both use the same hardened base image.
- **Three runs per configuration.** The ranges show the run-to-run spread. Between runs of 8.9.28,
  total broker CPU varied by up to ±8%, so differences below about 15% are not resolved by this data.
  All the headline differences are well outside that.
- **Export stall in one 8.10.9 run.** In `c8-aj-dmn810-s-r2-20261105`, 8.4% of records waited
  more than 1 s for the exporter (6.1 s mean). No 8.9.28 run did this. Command queue wait stayed
  normal, so the stall was on the export side. One occurrence in three runs cannot tell an 8.10.9
  exporter problem from an infrastructure stall, such as a slow Elasticsearch. Check the exporter
  and Elasticsearch panels of that run before concluding that export delays are always lower on
  8.10.9.
- **Idle baselines** are per version and use the 48 MiB DMN. They are used only for the CPU
  baseline. Their live-heap readings (0.14 GiB on 8.9.28, 2.0 GiB on 8.10.9) are not comparable,
  for the reason given under *Live heap* in [Interpretation](#interpretation).
- **Large-DMN coverage.** 30 minutes at 2 evaluations/s covers 3,600 of the 11,467 shuffled
  vectors. This is a fixed, identical sample for both versions, not full coverage.
- **Not collected.** GC logs and native memory tracking were enabled, but the files are on the
  broker volumes and were not retrieved (no kubectl access). Heap figures come from Micrometer only.
- **Profiles** were captured once per run (Batch A, 300 s). They show where the CPU goes, not the
  run-to-run variance.
- **Batch C is one run per configuration,** in a different window from Batches A and B. The 8.9.24
  CPU per evaluation borrows the 8.9.28 idle baseline, and its profiles are 100 s instead of 300 s.
  The 8.10.9 medium control saw Keycloak token errors (HTTP 500) at 14:42–14:43 UTC, with no failed
  evaluations.

## Reproduction

Deploy one load test per version and size, for example:

```bash
gh workflow run camunda-load-test.yml --repo camunda/camunda --ref ajanoni/dmn-8.10-benchmark \
  -f ref=ajanoni/dmn-8.10-benchmark \
  -f name=aj-dmn810-l-20261105 \
  -f scenario=dmn-large \
  -f secondary-storage-type=elasticsearch \
  -f target-version=stable-810 \
  -f orchestration-tag=8.10.9 \
  -f enable-optimize=false \
  -f stable-vms=true \
  -f ttl=2 \
  -f load-test-setup-helm-values="--set-string k6.tests.dmn-large.generator.env.DMN_SIZE_MIB=48 --set-string k6.tests.dmn-large.env.DMN_RATE=2 --set-string k6.tests.dmn-large.env.DMN_RAMP_UP=10m --set-string k6.tests.dmn-large.env.DMN_PRE_ALLOCATED_VUS=40"
```

- 8.9: `target-version=stable-89`, `orchestration-tag=8.9.28` (Batch C: `8.9.24`).
- Other sizes: `DMN_SIZE_MIB=0.25` / `DMN_RATE=40` (small), `DMN_SIZE_MIB=6` / `DMN_RATE=6` (medium).
- Idle baseline: `DMN_SIZE_MIB=48` / `DMN_RATE=0`.
- 8.10.9 on JRE 21: build the image once from `ajanoni/dmn-bench-8.10.9-jre21` (a deploy from that
  ref fails, because tag 8.10.9 has no `load-tests/setup`). Then deploy with
  `target-version=stable-810` and `reuse-tag=aj-dmn810j21-build-20261105-40c06bee` instead of
  `orchestration-tag`.

Collect the metrics for a window. To get the extended metrics, copy
[`extra-queries.yaml`](2026-11-dmn-8.9-vs-8.10-results/extra-queries.yaml) over
`load-tests/loadtestctl/src/loadtestctl/report/report-queries.yaml` on a branch, and dispatch the
workflow on that branch:

```bash
gh workflow run camunda-load-test-metrics.yaml --repo camunda/camunda --ref <branch-with-extra-queries> \
  -f namespace=c8-aj-dmn810-l-20261105 \
  -f duration-seconds=1800 \
  -f at=2026-11-05T20:25:00Z
```
