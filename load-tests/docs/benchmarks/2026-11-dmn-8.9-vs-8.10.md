# DMN benchmark: Camunda 8.9.28 vs 8.10.9 (small, medium and large DMN)

Date: 2026-11-05 · Branch: [`ajanoni/dmn-8.10-benchmark`](https://github.com/camunda/camunda/tree/ajanoni/dmn-8.10-benchmark)
· Based on [#65841](https://github.com/camunda/camunda/pull/65841) (`dmn-large` k6 scenario)

## TL;DR

With the same DMN and the same evaluation rate, 8.10.9 needs less broker CPU and memory than
8.9.28, and exports faster. The gap grows with the size of the DMN:

|     DMN size     | Broker CPU p50 | Broker RSS |  Exporting latency p99 | Processing latency p99 |
|------------------|---------------:|-----------:|-----------------------:|-----------------------:|
| Small (0.25 MiB) |       **−24%** |   **−44%** |               **−42%** |                   −16% |
| Medium (6 MiB)   |       **−52%** |   **−35%** |               **−62%** |               **−66%** |
| Large (48 MiB)   |       **−86%** |       −12% | **−97%** (891 → 25 ms) | **−97%** (869 → 22 ms) |

On the large DMN, 8.9.28 has a long latency tail (p99 close to 0.9 s) and a small export
backlog that does not drain. 8.10.9 stays flat at about 25 ms. Peak heap used is about
the same on both, because the parsed model fills the same space in a 6 GiB heap. See
[Interpretation](#interpretation) for details.

## Purpose

These recent DMN changes on `stable/8.10` should lower the cost of evaluating and exporting
decisions, especially for large decision graphs:

|                                                                              Change                                                                              | In 8.10.9 | In 8.9.28  |
|------------------------------------------------------------------------------------------------------------------------------------------------------------------|:---------:|:----------:|
| dmn-scala 1.12.6 ([#67857](https://github.com/camunda/camunda/pull/67857))                                                                                       |     ✅     | ❌ (1.11.4) |
| Cached DMNs release their parsed XML model ([#67792](https://github.com/camunda/camunda/pull/67792))                                                             |     ✅     |     ❌      |
| Keep decision export cost linear ([#67998](https://github.com/camunda/camunda/pull/67998), 8.9 backport [#67997](https://github.com/camunda/camunda/pull/67997)) |     ✅     |     ✅      |
| Size exported records instead of Kryo ([#67883](https://github.com/camunda/camunda/pull/67883))                                                                  |     ✅     |     ❌      |

The benchmark compares the **latest released images** of both minors, `camunda/camunda:8.9.28`
and `camunda/camunda:8.10.9`. Most of the difference comes from the DMN changes above, but not
all of it: the two minors also differ in other engine, exporter and Helm chart changes.

## Setup

Six load tests ran **in parallel** on the benchmark GKE cluster (2 versions × 3 DMN sizes).
Each one used the `dmn-large` scenario, deployed through the
[`camunda-load-test.yml`](../../../.github/workflows/camunda-load-test.yml) workflow.

|         Item          |                                                          Value                                                          |
|-----------------------|-------------------------------------------------------------------------------------------------------------------------|
| Orchestration cluster | 3 brokers, 6 partitions, replication factor 3                                                                           |
| Broker resources      | 3 CPU / 10 GiB limit, `-XX:MaxRAMPercentage=60` (≈ 6 GiB heap), `cpuThreadCount=3`, `ioThreadCount=3`                   |
| Broker disk           | 64 GiB SSD PVC                                                                                                          |
| Message size          | `camunda.cluster.network.max-message-size=128MB`, 64 MB multipart limit                                                 |
| Secondary storage     | Elasticsearch (ECK), Camunda exporter                                                                                   |
| Optimize              | disabled                                                                                                                |
| Nodes                 | `stable-vms=true` (n2-standard-4, non-preemptible)                                                                      |
| Helm setup            | `load-tests/setup/stable-89` for 8.9.28, `load-tests/setup/stable-810` for 8.10.9                                       |
| Platform values       | `values/camunda-platform-values-defaults.yaml` + `values/camunda-platform-values-dmn-large.yaml` + Elasticsearch values |
| Workload              | k6 `dmn-large` test only (no BPMN starter or workers), k6 runner 1 CPU / 2 GiB                                          |

To run the `dmn-large` scenario on `stable-810` and `stable-89`, this branch adds the overlay to
both setups and gives the k6 client the `DECISION_DEFINITION` permissions it needs.

## Input

The k6 init container builds the DMN with
[`generate_tariff_dmn.py`](../../setup/charts/load-test-setup/k6/generators/generate_tariff_dmn.py).
The output is deterministic, so both versions evaluated byte-identical models. Every model has
the same shape: a freight-tariff decision graph with 12 decisions, three large FIRST-hit tables,
FEEL combiner tables and one top decision that requires the whole graph. Only the number of rules
changes with the size.

|  Size  | `DMN_SIZE_MIB` | File size | Rules | Test vectors | Rate (`DMN_RATE`) |
|--------|---------------:|----------:|------:|-------------:|------------------:|
| Small  |           0.25 |  0.25 MiB |    56 |        3,044 |  40 evaluations/s |
| Medium |              6 |   6.0 MiB |   972 |        3,960 |   6 evaluations/s |
| Large  |             48 |  48.0 MiB | 8,479 |       11,467 |   2 evaluations/s |

- The rate goes down as the size goes up, so that both versions stay below saturation and the
  comparison measures **cost per evaluation**, not maximum throughput.
- Executor: k6 `ramping-arrival-rate`, `DMN_RAMP_UP=10m`, `DMN_PRE_ALLOCATED_VUS=40`.
- The default `DMN_DEPTH_MIX` walks every vector: targeted vectors (one per reachable rule),
  random, payload-like and fall-through vectors. Every rule of the model is exercised.
- Each test deploys the DMN once, then evaluates the top decision through
  `POST /v2/decision-definitions/evaluation`.

## Method

- Load tests deployed at about 19:27–19:33 UTC. After the 10-minute ramp, there was a settle
  period.
- **Measurement window: 2026-11-05 19:55:00 → 20:25:00 UTC (30 min)**, the same for all six
  runs.
- Metrics were collected with
  [`camunda-load-test-metrics.yaml`](../../../.github/workflows/camunda-load-test-metrics.yaml)
  (`duration-seconds=1800`, `at=2026-11-05T20:25:00Z`), which runs `loadtestctl report` against
  the benchmark Prometheus. The queries are defined in
  [`report-queries.yaml`](../../loadtestctl/src/loadtestctl/report/report-queries.yaml):
  - **CPU p50 / p99**: quantile over time of the CPU rate of the busiest broker pod.
  - **RSS**: highest container RSS of any broker pod.
  - **Heap**: highest JVM heap used of any broker pod during the window. This is the peak in-use
    heap, **not** the live set after GC.
  - **Exporting latency**: `histogram_quantile` of `zeebe_exporting_latency` (time from writing
    a record to the log until the exporter picks it up), over the whole window.
  - **Exporting / processing backlog**: average over the window of the highest per-partition
    backlog.
  - **Elasticsearch**: CPU and heap of the ES pods, and indexed documents per second.

## Interpretation

- **CPU.** For each evaluation, 8.10.9 uses much less broker CPU, and the gain grows with model
  size: −24% for the small model, −52% for medium, −86% for large. On 8.9.28, the large model at
  only 2 evaluations/s used more CPU (0.63 cores) than the small model at 40 evaluations/s. On
  8.10.9, it uses 0.09 cores. This matches the dmn-scala 1.12.x evaluation improvements.
- **Latency and exporter.** On 8.9.28, processing p99 and exporting p99 grow with model size
  and reach about 0.9 s for the large model. A backlog stays in the exporter for the whole
  window. On 8.10.9, both p99 values stay between 20 and 40 ms for every size, and the exporter
  backlog is 0 for medium and large. The exporting latency tracks the processing latency: the
  exporter waits on the stream processor, which is busy evaluating the large graph.
- **Throughput.** The configured rate was the same for both versions, but 8.9.28 processed
  11% fewer records/s on the large model. 8.9.28 did not quite keep up with 2 evaluations/s at
  48 MiB, so its large-model figures are on the edge of saturation. A higher rate would make the
  gap larger, not smaller.
- **Memory.** Broker RSS is lower on 8.10.9 for every size (−44%, −35%, −12%). The *peak heap
  used* is about the same for the large model (5.6 vs 5.7 GiB of ≈ 6 GiB). That metric shows how
  far the heap fills between GC cycles, not the retained set, so it cannot show the effect of
  releasing the parsed XML model (#67792). To compare retained memory, use the JVM
  *heap after GC* / *old gen* panels of the Zeebe dashboard (links below).
- **Elasticsearch.** 8.10.9 indexes about 35–42% fewer documents per second for the same
  number of evaluations, and ES CPU drops for the small model (−42%). This suggests 8.10 writes
  fewer documents per decision evaluation (exporter and schema changes between the two minors).
  ES CPU is otherwise low in all runs, so ES was never the bottleneck.

## Caveats

- There was **one run per configuration**. The runs were in parallel on stable VMs, so the
  six clusters shared the same time window and node pool. Small differences (< 10%) are within
  the noise; the large deltas above are well outside it.
- The comparison is **8.9.28 vs 8.10.9**, not one isolated commit. Changes other than the DMN
  fixes (exporter, Helm chart and engine) are also included.
- 8.9.28 already contains the linear-export fix (#67997). The DMN-specific differences are
  therefore dmn-scala 1.11.4 → 1.12.6 and the release of the parsed XML model.
- The rates are deliberately below saturation. This benchmark measures **resource cost and
  latency at a fixed load**, not maximum throughput.
- Client-side k6 metrics (evaluation latency, failed checks) are not part of the `loadtestctl`
  report. See the k6 dashboards for them.

## Reproduction

Deploy one load test per version and size, for example:

```bash
gh workflow run camunda-load-test.yml --repo camunda/camunda --ref ajanoni/dmn-8.10-benchmark \
  -f ref=ajanoni/dmn-8.10-benchmark \
  -f name=aj-dmn810-l-20261105 \
  -f scenario=dmn-large \
  -f secondary-storage-type=elasticsearch \
  -f target-version=stable-810 \
  -f orchestration-tag=8.10.9 \
  -f enable-optimize=false \
  -f stable-vms=true \
  -f ttl=2 \
  -f load-test-setup-helm-values="--set-string k6.tests.dmn-large.generator.env.DMN_SIZE_MIB=48 --set-string k6.tests.dmn-large.env.DMN_RATE=2 --set-string k6.tests.dmn-large.env.DMN_RAMP_UP=10m --set-string k6.tests.dmn-large.env.DMN_PRE_ALLOCATED_VUS=40"
```

For 8.9, use `target-version=stable-89` and `orchestration-tag=8.9.28`. For the other sizes,
use `DMN_SIZE_MIB=0.25 / DMN_RATE=40` (small) and `DMN_SIZE_MIB=6 / DMN_RATE=6` (medium).

Collect the metrics for the same window:

```bash
gh workflow run camunda-load-test-metrics.yaml --repo camunda/camunda \
  -f namespace=c8-aj-dmn810-l-20261105 \
  -f duration-seconds=1800 \
  -f at=2026-11-05T20:25:00Z
```
